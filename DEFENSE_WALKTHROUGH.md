# BeautyFlow — сценарий защиты на 5 минут

Подготовка: запустить MongoDB и приложение на `http://localhost:5174`, проверить demo-данные и свободный слот. Для входа владельца использовать `owner@demo.local` / `demo-password-123` — demo-вход завершается без ручного ввода OTP. Google OAuth credentials добавлены в локальный `.env`, но вход через Google и разрешённый OAuth origin в этом проходе не проверялись; для стабильного показа используйте demo-аккаунт. Порт `5173` занят.

## Сценарий

### 0:00–0:30 — лендинг

- **URL:** `http://localhost:5174/`
- **Действия:** показать первый экран и переключить светлую/тёмную тему, затем нажать «Начать бесплатно».
- **Сказать:** «BeautyFlow — CRM и онлайн-запись для салонов: владелец управляет расписанием, командой, клиентами и оплатами в одном месте. Лендинг сразу показывает продукт и ведёт к регистрации без лишних шагов».

### 0:30–1:00 — вход и обзор

- **URL:** `http://localhost:5174/login`, после входа — `/app/dashboard`
- **Действия:** войти демо-аккаунтом, показать KPI и ближайшие записи на дашборде.
- **Сказать:** «После входа владелец видит операционную сводку и ближайшие визиты. Данные принадлежат выбранному салону, а доступ к действиям определяется ролью участника».

### 1:00–2:00 — календарь и создание записи

- **URL:** `http://localhost:5174/app/calendar`
- **Действия:** выбрать рабочую дату и неделю или день, нажать на свободную ячейку, выбрать клиента, услугу и мастера, нажать «Создать запись». Показать появившуюся карточку и статус.
- **Сказать:** «Календарь показывает рабочие интервалы, занятые слоты и записи по мастерам; запись создаётся прямо из свободного слота. При конфликте система повторно проверяет доступность на сервере, поэтому визуально свободное время не приводит к двойному бронированию».

### 2:00–3:00 — публичная запись и управление визитом

- **URL:** `http://localhost:5174/b/demo-salon`
- **Действия:** на `/b/demo-salon` выбрать услугу, мастера, дату и слот, заполнить контакт, подтвердить визит, затем нажать «Управлять записью».
- **Сказать:** «Клиент записывается через отдельную страницу салона; свободные слоты вычисляются по расписаниям команды. После бронирования клиент получает ссылку управления, где может перенести или отменить визит».

### 3:00–3:30 — оплаты

- **URL:** `http://localhost:5174/app/payments`
- **Действия:** показать журнал оплат, суммы и статусы; открыть доступную запись/оплату и обратить внимание на связь с визитом и клиентом.
- **Сказать:** «Оплаты привязаны к визиту и клиенту, а журнал показывает метод, сумму и состояние операции. Это позволяет сверять выручку с расписанием без отдельного списка несвязанных платежей».

### 3:30–4:15 — команда

- **URL:** `http://localhost:5174/app/staff`
- **Действия:** открыть сотрудника, показать профиль и вкладки расписания, исключений, услуг и доступа.
- **Сказать:** «Для каждого мастера настраиваются график, исключения, услуги и права доступа. Эти настройки влияют на то, какие слоты можно предложить клиенту и кто может менять данные».

### 4:15–5:00 — клиенты и завершение

- **URL:** `http://localhost:5174/app/customers`
- **Действия:** найти клиента, открыть карточку и показать историю визитов и платежей.
- **Сказать:** «Карточка объединяет контакты и историю взаимодействий, поэтому администратор видит контекст перед следующим визитом. В итоге публичная запись, календарь, команда, клиентская база и оплаты связаны одним tenant-контуром».

## Технические решения для рассказа

- **`occupiedKeys`:** уникальные ключи занятости для временных интервалов записи. Они служат последним ограничителем от пересечения визитов одного мастера даже при одновременных запросах.
- **`tenantPlugin`:** автоматически добавляет границу текущего бизнеса к операциям с tenant-данными и не даёт запросу одного салона читать или менять документы другого.
- **`withTransaction`:** объединяет связанные изменения в MongoDB-транзакцию: всё фиксируется целиком либо откатывается, если одна из частей не прошла.
- **Защита от гонок:** сервер атомарно резервирует занятые интервалы и обрабатывает повтор запроса по idempotency key. В конкурентном сценарии из 20 запросов один создаёт запись (`201`), остальные получают конфликт (`409`), а не создают дубликаты.
- **Тесты:** ранний gate содержал **118 тестов**; текущий Vitest-набор — **125 тестов в 34 файлах**. Отдельный race-набор — 2/2; полный Playwright E2E — **23/23**, включая OTP-регистрацию, вход demo owner/master и создание записи в календаре.
- **Linear-стиль интерфейса:** использованы ясная визуальная иерархия, плотные рабочие списки, сдержанная палитра, единые состояния и предсказуемая навигация. Это ориентир на читаемость и скорость работы, а не копия продукта Linear.

## Частые вопросы комиссии

### Как вы защищаете систему от овербукинга?

Публичный экран заранее показывает только доступное время, но окончательное решение принимает сервер. При создании он повторно проверяет расписание, занятость и блокировки; `occupiedKeys` и уникальные индексы закрывают конфликт между одновременными запросами, а транзакция сохраняет связанные изменения целиком. Повтор того же запроса не создаёт дубль благодаря idempotency key.

### Как изолированы данные разных бизнесов?

Каждая запись принадлежит `businessId`; `tenantPlugin` автоматически ограничивает запросы активным tenant и не позволяет передать чужой ID как обход границы. Роль и permission-проверки дополнительно ограничивают доступ к действиям внутри бизнеса. Это проверяется тестами прямых запросов между tenant A и B.

### Почему MongoDB, а не PostgreSQL?

Для этого проекта выбран документный формат MongoDB: запись визита хранит согласованный снимок услуги и связанные детали, а Mongoose упрощает работу с tenant-scoped документами. Там, где нужны изменения сразу в нескольких коллекциях, используются транзакции replica set и уникальные индексы. PostgreSQL тоже подходит; выбор не означает, что MongoDB лучше для любого CRM.

### Что ещё не сделано?

Реальное production-развёртывание, восстановление из production backup и доставку через настроенный SMTP здесь не проверяли. Google OAuth требует заданных credentials и разрешённого origin; email-код и демо-вход проходят локальные проверки, но полный аудит всех production-операций остаётся отдельной задачей.

### Как система масштабируется?

API не хранит состояние конкретного запроса в памяти, поэтому его можно запускать несколькими экземплярами за балансировщиком; сессии и бизнес-данные находятся в MongoDB. Worker можно масштабировать отдельно, контролируя нагрузку на БД и email-провайдера. Для роста сначала повышают ресурсы replica set и измеряют узкие места; шардирование рассматривают только после нагрузочных замеров, это не заявляется как уже проверенная часть проекта.

## Деплой для демонстрации

### Локальный MongoDB replica set через Docker Compose

В проекте `docker-compose.yml` поднимает MongoDB 8 с одноузловым replica set `rs0` и открывает его на `localhost:27018`:

```sh
docker compose up -d mongo
npm install
npm run migrate
npm run seed
npm run dev
```

В `.env` указать подключение, например `MONGODB_URI=mongodb://localhost:27018/nextappointments?replicaSet=rs0&directConnection=true`, `MONGODB_DB_NAME=nextappointments`, а также локальные `TOKEN_PEPPER` и `CRON_SECRET`. `npm run dev` запускает API, клиент на `5174` и локальный notification worker. Не заменять существующий `.env` и не коммитить секреты.

### MongoDB Atlas Free (ранее M0)

Для учебного demo создать в Atlas Free cluster, добавить database user и разрешить в Network Access только IP сервера/рабочей станции. Скопировать выданный Atlas connection string с базой `nextappointments`, URL-кодировать пароль и сохранить строку только как `MONGODB_URI` в `.env`; затем выполнить миграции и, только для demo-данных, `npm run seed`. Free cluster — трёхузловой replica set и подходит для проверки транзакций, но ограничен 0,5 GB и 100 операциями/с, не имеет встроенных backups и не должен представляться production-настройкой. [Актуальные ограничения Atlas Free](https://www.mongodb.com/docs/atlas/reference/free-shared-limitations/).

Перед реальным публичным запуском использовать отдельный replica set, защищённые credentials, SMTP и HTTPS proxy; пройти production release checklist из [`docs/DEPLOY.md`](docs/DEPLOY.md). Настоящий production deploy этого проекта пока не подтверждён.
