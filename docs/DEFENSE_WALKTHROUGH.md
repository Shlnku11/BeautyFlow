# Устаревшая копия сценария защиты

Актуальная 5-минутная версия находится в [`../DEFENSE_WALKTHROUGH.md`](../DEFENSE_WALKTHROUGH.md). Ниже сохранён прежний расширенный сценарий на 7–9 минут; используйте его только как дополнительный справочный материал.

Ориентир по времени: 7–9 минут, затем вопросы. Сценарий рассчитан на локальную демонстрацию и seeded demo-данные.

## Перед защитой

1. Установить Node.js 24 и зависимости (`npm install`).
2. Проверить `.env`: MongoDB replica set доступен на `localhost:27018`, указаны локальные `TOKEN_PEPPER` и `CRON_SECRET`.
3. Если демо-база ещё не заполнена или её нужно вернуть в исходное состояние, выполнить `npm run seed` при `NODE_ENV=development`.
4. Запустить `npm run dev`. Команда поднимает API на `http://localhost:3000`, клиент на `http://localhost:5174` и worker уведомлений.
5. Убедиться, что `http://localhost:3000/api/health` отвечает, а страница `http://localhost:5174` открывается.
6. Для входа использовать владельца `owner@demo.local` или мастера `master@demo.local`, пароль `demo-password-123`. В локальном dev-клиенте для этих двух demo-аккаунтов OTP подтверждается автоматически; фиксированный код `000000` ограничен development и этими seeded-аккаунтами. Не демонстрировать этот режим как production-политику.

## Сценарий показа

### 1. Задача и пользователи — 45 секунд

BeautyFlow объединяет онлайн-запись и ежедневную работу салона: владелец управляет расписанием, услугами, командой, клиентами и оплатами; мастер видит свой рабочий день и записи. Начать с публичной страницы `/b/demo-salon`, затем показать CRM.

### 2. Путь клиента — 1 минута

Открыть `/b/demo-salon`. Показать оформление салона и публичную запись: клиент выбирает услугу, специалиста и доступное время, затем вводит контактные данные. Отметить, что доступность строится на расписании и занятости мастеров. Не подтверждать оплату через платёжный шлюз: подключённый production-провайдер платежей в локальном демо не настроен.

### 3. Обзор владельца — 1 минута

Войти как `owner@demo.local` и открыть `/app/dashboard`. Показать краткий обзор дня, ближайшие записи и переходы к основным разделам. Подчеркнуть, что это рабочая панель, а не отдельная таблица-отчёт.

### 4. Расписание и записи — 1,5 минуты

Открыть `/app/calendar`, переключить день, неделю и месяц. Показать фильтр мастеров и визуальное положение записей по времени. Создать тестовую запись через кнопку добавления, показать поля формы, затем закрыть форму без сохранения, если новая запись не нужна для дальнейшей демонстрации. Перейти в `/app/appointments`, показать статусы и действия над записью.

### 5. Клиенты и управление салоном — 1,5 минуты

Коротко открыть `/app/customers`, `/app/staff` и `/app/services`. Связать разделы: запись относится к клиенту, услуге и специалисту, а расписание учитывает назначенного мастера. При наличии времени показать `/app/payments` и `/app/settings`.

### 6. Роль мастера и мобильный интерфейс — 1 минута

Выйти и войти как `master@demo.local`, открыть `/app/my-day`. Показать ограниченный рабочий вид мастера с его записями. Для мобильного UX открыть заранее снятые скриншоты из `docs/screenshots/redesign/after/`: `mobile-owner-dashboard-light.png`, `mobile-owner-calendar-month-dark.png` и `mobile-master-my-day-dark.png`. Съёмка Playwright выполнена при ширине 390 px; проверка не обнаружила горизонтального переполнения.

### 7. Техническая часть и завершение — 1 минута

Стек проекта: React, TypeScript и Vite в клиенте; Express 5 и TypeScript в API; MongoDB replica set и Mongoose для данных; общие типы и Zod-схемы между слоями. Локальная проверка типов и production build проходят. Клиентские страницы загружаются отдельными маршрутными чанками. В dev-режиме email-провайдер Console выводит тело письма и OTP в терминал worker-процесса.

## Если что-то пошло не так

- **Салон или данные не видны:** проверить подключение MongoDB и выполнить `npm run seed` в development.
- **Клиентская страница не отвечает:** проверить порт `5174`; API и health endpoint работают на порту `3000`.
- **Письмо не пришло:** посмотреть вывод процесса `notifications`; Console-провайдер предназначен для локальной разработки.
- **Нельзя войти в Google:** это ожидаемо без `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` и настройки OAuth origin в Google Cloud Console. Для демонстрации использовать email/password demo-аккаунт.
- **Не изменять demo-данные перед защитой:** повторный seed восстанавливает часть данных для показа; подготовить базу заранее и проверить сценарий в отдельной сессии.

## Границы текущей демонстрации

- Google OAuth UI подключён, но реальный вход требует credentials и настройки Google Cloud.
- OTP-код для demo-пользователей и автоматическое подтверждение действуют только в локальной разработке. Обычный режим email использует доставку через настроенного провайдера; Console выводит сообщение только в терминал.
- Репозиторий содержит инструкции по production-развёртыванию, но production deployment, домен, TLS и SMTP в рамках этой демонстрации не подтверждены.
- Сравнительные скриншоты — визуальный обзор с публичными страницами Linear, Vercel и Stripe; они служат ориентирами по композиции и не являются снимками их закрытых CRM.

## Ответы на ожидаемые вопросы

- **Кто пользуется системой?** Владелец/администратор салона и мастер; публичная запись предназначена клиентам.
- **Что проверено в этом релизе?** TypeScript typecheck, production build, auth-flow проверки и ручной вход demo-аккаунтов через Playwright; мобильные CRM-снимки проверены на ширине 390 px.
- **Что нужно для реального запуска?** Настроить Google OAuth credentials (если OAuth нужен), SMTP и production MongoDB, затем развернуть API, worker и клиент за HTTPS reverse proxy и провести staging-проверку.
