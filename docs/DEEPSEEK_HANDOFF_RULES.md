# DEEPSEEK_HANDOFF_RULES.md — Правила передачи задач внешнему исполнителю (Codex Luna 6)

<!-- CHANGED: A2a -->
**Исполнитель — Codex Luna 6** (модель «Luna 6»; ранее в документах фигурировал DeepSeek). Имя файла историческое и сохранено ради ссылок из других документов; правила не привязаны к конкретной модели. Термины «исполнитель» и «внешний чат» ниже означают один и тот же субъект.

Документ описывает **правила и шаблон**. Task-пакеты — `docs/tasks/`. Claude остаётся архитектором и ревьюером: исполнитель пишет код по жёстким границам, Claude проверяет и сливает.

**Режимы работы исполнителя** (фиксируются в каждом задании строкой `РЕЖИМ:`):
- **Режим R (репозиторий):** у исполнителя есть рабочая копия проекта; он читает файлы, правит **только** файлы из ALLOWED, запускает указанные команды (`typecheck`, `lint`, тесты) и возвращает отчёт. По умолчанию принимается для Codex Luna 6 (подтверждается владельцем).
- **Режим C (чат):** исполнитель видит только вставленный контекст и возвращает полный код файлов в ответе.

## 1. Принципы

1. Исполнитель получает **минимально достаточный** контекст и ничего лишнего: в режиме C — только вставленное в задание; в режиме R — задание указывает, какие файлы читать (ALLOWED + перечисленные зависимости), остальные не читаются и не меняются. <!-- CHANGED: A2a -->
2. Контракты (DATA_MODEL, API_CONTRACTS, PERMISSIONS_MATRIX, типы/интерфейсы) — **неизменяемый вход**. Чат реализует, а не проектирует.
3. Результат принимается только после проверки Claude (§8). Без проверки код не сливается.
4. Любая неоднозначность → чат **останавливается и задаёт вопрос**, а не выбирает сам.

## 2. Единица передачи

| Случай | Правило |
|---|---|
| Один независимый файл (чистая функция, Zod-схема, UI-компонент без побочных зависимостей) | Можно отдать отдельному чату |
| Связанная группа файлов (модель + репозиторий + сервис + маршрут одной функции; компонент + хук + схема) | **Один чат на всю группу**, иначе расходятся имена и импорты |
| Файлы, меняющие общие контракты (`shared/schemas`, `shared/error-codes`, `defineRoute`, `tenantPlugin`, `permissions.ts`) | Не передаются — делает Claude |
| Миграции, tenant-guard, auth/сессии, `withTransaction`, `defineRoute`, `AppError`-классы, UI-компоненты дизайн-системы, `api-client`, `hooks/use-api` | **Не передаются никогда** — пишет Claude (полный список — §5, §12) |
| Транзакционные сервисы записи и оплат (`BookingService` 6b/6c, `PaymentService`) | Передаются **только как зависимая стопка** (repo + service + route + tests) на готовых `withTransaction`, `defineRoute`, `occupiedKeys`-инварианте, с **усиленным ревью** (§8, п. 6) |

**Правило единицы передачи:** независимые файлы — отдельная задача; связанные стопки (repo + service + route + tests) — **одна задача, один запуск исполнителя**. Классификация и примеры — §11. <!-- CHANGED: A7 -->

Размер задачи: до ~8 файлов и ~1 200 строк результата; больше — делить по границам функции.

## 3. Пакет контекста (что получает чат)

1. **Цель** одной фразой и **этап** разработки.
2. **Exact context:** дословные фрагменты нужных документов (не пересказ): секции DATA_MODEL по затронутым коллекциям; блоки API_CONTRACTS по затронутым ID; строки PERMISSIONS_MATRIX; нужный алгоритм (BOOKING_ENGINE_SPEC §…); токены дизайна для UI.
3. **Allowed files** — точный список путей, которые чат создаёт/меняет.
4. **Forbidden files** — всё остальное; явно перечислены критичные: контракты, конфиги, `package.json`, миграции, чужие модули.
5. **Interfaces/types** — готовые сигнатуры зависимостей, которые чат **использует, но не пишет** (`TenantContext`, интерфейсы репозиториев соседних модулей, `AppError`-классы, `defineRoute`).
6. **Acceptance criteria** — проверяемый список (поведение, коды ошибок, права, изоляция).
7. **Tests** — какие тесты чат пишет сам (файлы и сценарии) и какие фикстуры использует (`world-ab.ts` и т.д.).
8. **Стандарты:** CODING_STANDARDS целиком или релевантные секции (§1, §2, §4–§9).
9. **Формат ответа** (§7).

## 4. Allowed / forbidden — правила

- Чат может создавать/менять **только** файлы из Allowed. Любой файл вне списка = нарушение, результат отклоняется целиком.
- Нужна правка вне списка → чат описывает её текстом («нужно изменить X, потому что Y») и не делает сам.
- Чат не меняет сигнатуры чужих функций, не добавляет поля в чужие DTO.
- **Режим R:** проверка границ автоматическая — `git diff --name-only` (и неотслеживаемые файлы) обязаны быть подмножеством ALLOWED; в файлах-заготовках маршрутов (`src/app/api/**/route.ts`) допустимо менять **только тело `handler`**, но не `id`, `permission`, схемы, `rateLimit`; в файлах-заготовках репозиториев/сервисов — только тела методов, не сигнатуры. <!-- CHANGED: A7 -->

## 5. Неприкосновенные контракты

Нельзя без отдельного письменного разрешения:
- менять имена/пути/методы/коды ответов API и формат конвертов;
- менять схему БД: поля, типы, индексы, имена коллекций; **придумывать новые сущности и поля**;
- менять права и их ключи;
- менять Zod-схемы в `src/shared`, коды ошибок, дизайн-токены;
- добавлять зависимости (в т.ч. «маленькие утилиты»); использовать только то, что в `package.json` и разрешённом списке задания;
- переименовывать что-либо: **имена сущностей и полей только из DATA_MODEL**.

**Никогда не отдаются исполнителю (пишет только Claude) — A7:** `src/server/auth/**`, `tenantPlugin` (`src/server/db/plugins/tenant.ts`), `defineRoute` (`src/server/http/define-route.ts`), `withTransaction` (`src/server/db/transactions.ts`), `migrations/**`, `AppError`-классы (`src/server/http/errors.ts`), UI-компоненты дизайн-системы (`src/components/ui/**`), `src/lib/api-client.ts`, `src/hooks/use-api.ts`. Исполнитель **импортирует** их, но не создаёт, не копирует и не «улучшает». Нужно изменение — описывается текстом как запрос Claude. <!-- CHANGED: A7 -->

## 6. Запреты на содержимое

- **Mock-данные**, заглушки и `TODO` вместо работающей логики в основных функциях; фиктивные ответы API; `Math.random` вместо реальных данных.
- `any`, `@ts-ignore`; прямой доступ к БД из UI; `businessId` из тела/query; секреты в коде; `console.log`; `populate`; float для денег.
- Копирование кода из reference-проекта (PHP) и его «перевод» построчно; сторонний код без указания источника/лицензии.
- Изменение существующих исходников вне Allowed; «улучшения по ходу» и рефакторинг несвязанного кода.
- Хардкод русских строк в компонентах (только словарь).

## 7. Что обязан вернуть чат

<!-- CHANGED: A2a -->
**Режим R:** изменения вносятся прямо в файлы из ALLOWED. Вместо «полного кода в ответе» исполнитель возвращает: список изменённых/созданных файлов, `git diff --stat`, **фактический вывод** команд (`npm run typecheck`, `npm run lint`, указанные тесты) без пересказа, пункты 3–7 ниже. Заявление «тесты зелёные» без приложенного вывода не принимается.
**Режим C:** все пункты ниже.

1. **Полный код каждого файла целиком** (не диффы, не «остальное без изменений», не многоточия).
2. **Список файлов** с путями (совпадает с Allowed; лишних нет).
3. **Список всех импортов** по файлам (внешние пакеты отдельно — для проверки, что новых зависимостей нет; внутренние — для проверки границ слоёв).
4. **Список допущений и открытых вопросов** (что было неоднозначно, как поступил — либо «остановился»).
5. **Тесты** (полный код) и перечень сценариев, которые они покрывают, по каждому acceptance-критерию.
6. **Самопроверка:** таблица «критерий → файл/строка/тест»; явное заявление «новых зависимостей нет», «контракты не менялись», «mock-данных нет».
7. Что **не** сделано/не проверено (честно).

## 8. Чек-лист проверки Claude перед слиянием

1. **Границы:** изменены только Allowed файлы; нет посторонних правок. В режиме R — `git diff --name-only` + неотслеживаемые файлы ⊆ ALLOWED; в заготовках маршрутов изменено только тело `handler`, в заготовках репозиториев/сервисов — только тела методов. <!-- CHANGED: A2a -->
2. **Контракты:** сравнить с DATA_MODEL/API_CONTRACTS/PERMISSIONS построчно (имена полей, коды, роли); новых сущностей/полей нет.
3. **Зависимости:** diff импортов; новых пакетов нет; слои соблюдены (`server`/`shared`/UI).
4. **Мультитенантность:** `ctx` везде, `businessId` только из `ctx`; кросс-ссылки проверяются; нет запросов мимо репозитория; strict-схемы.
5. **Права:** ключи прав на месте; `own`-область реализована фильтром; 404/403 по правилам.
6. **Корректность логики:** алгоритмы соответствуют спецификации (время, DST, деньги — целые); транзакции там, где нужны; идемпотентность; обработка ошибок. **Усиленное ревью** (построчное, с проверкой гонок) для стопок: `STF-02`, `BLK-02`, `APT-02`, `APT-05`, `APT-06`, `PUB-06`, `PUB-09/10`, `PAY-02`, `PAY-06`, воркер уведомлений: все `withTransaction`, условные обновления, `E11000`-обработка и пересчёт `occupiedKeys` проверяются вручную. <!-- CHANGED: A2a -->
7. **Безопасность:** нет секретов; токены хэшируются; нет утечки полей в DTO; нет NoSQL-инъекций (только строки из Zod); логирование без ПД.
8. **Качество:** `any`, mock, TODO, `console.log`, мёртвый код — отсутствуют; соблюдены именование и стандарты.
9. **Лицензия:** нет следов копирования кода из reference/сторонних источников.
10. **Тесты:** покрывают каждый acceptance-критерий, включая A vs B и роли; **реально запущены** (`lint`, `typecheck`, тесты, `build`) — Claude перезапускает их сам, а не доверяет заявлению исполнителя; результаты записаны.
11. **UI:** состояния loading/empty/error/success; доступность (labels, фокус, клавиатура); токены, без произвольных цветов; стекло только по whitelist.
12. Решение: **принять** / **вернуть с замечаниями** (список конкретных правок) / **переделать**. После двух возвратов задача переходит Claude.

## 10. Порядок слияния

Пакеты сливаются в порядке зависимостей (MASTER_ARCHITECTURE §19). Один пакет — одна ветка/коммит. После слияния Claude запускает проверки этапа (lint, typecheck, unit, integration, миграции, build, A/B-изоляция, роли) и обновляет `PROGRESS.md`. Обнаруженное расхождение контракта → правка документа **сначала** (с разрешения), код — потом.

## 11. Классификация файлов: независимые файлы и зависимые стопки <!-- CHANGED: A2a, A7 -->

**Независимый файл** — не импортирует ничего из `src/server/**` (кроме чистых функций `src/server/domain/*`, уже написанных Claude), из `src/components/**` и из `src/hooks/**`; допустимы только `@/shared/**`, стандартная библиотека и разрешённые пакеты. Проверяется отдельно, одним небольшим тестом, поэтому **одна задача — один файл (+ тест)**.
Примеры (по этапам плана): `src/server/domain/dashboard-period.ts` (границы периода в поясе бизнеса, этап 10), `src/server/notifications/dedupe-key.ts` и `backoff.ts` (этап 8), `src/server/notifications/templates/ru/*.ts` (рендер писем из типизированных данных, этап 8), `src/server/domain/phone.ts` (нормализация телефона по `countryCode`, этап 5).

**Зависимая стопка** — файлы, которые вместе реализуют одну функцию и ссылаются друг на друга: **repo + service + route + tests** (+ для UI: компоненты функции + хук `use-<feature>.ts` + страница). **Одна задача, один запуск исполнителя** на всю стопку: иначе расходятся имена, импорты и допущения.
Примеры: стопка «Staff» (`staff-repository.ts`, `staff-service.ts`, `src/app/api/staff/**/route.ts`, `tests/api/staff.test.ts`, `tests/integration/staff.test.ts`); стопка «Customers»; стопка «Публичная запись 6c» (`PUB-01…10`); UI-стопка «Customers UI» (`components/features/customers/*`, `hooks/use-customers.ts`, страницы `/app/customers`).

**Правила:** (1) стопка не делится между запусками; (2) независимый файл не включается в стопку «заодно» — иначе смешиваются критерии приёмки; (3) если «независимый» файл при реализации потребовал импорт из `server`/`components` — это стопка, исполнитель останавливается и сообщает; (4) размер стопки ≤ ~8 файлов и ≈1 200 строк (§2) — большая функция делится по границе endpoint-группы, но каждая часть остаётся целой стопкой.
