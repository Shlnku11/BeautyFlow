# TESTING_STRATEGY.md — Стратегия тестирования

Тестовых инструментов в проекте пока нет (в `package.json` нет `test`-скрипта). Инструменты ниже — **предложение**, устанавливаются только с разрешения (Этап 1): `vitest`, `mongodb-memory-server` (режим replica set), `@playwright/test`, `@axe-core/playwright`, `supertest`-подобный вызов Route Handlers напрямую.

## 1. Принципы и пирамида

Много быстрых unit-тестов чистой логики → интеграционные тесты с **реальным MongoDB replica set** (транзакции и индексы — часть поведения, моки БД запрещены) → API-тесты контрактов → немного E2E. Каждый этап разработки приносит свои тесты; функция не «готова» без них (PRODUCT_SPEC §7). Тесты детерминированы: время (`now`) и случайность инжектируются; нет зависимости от реальной почты/сети.

## 2. Unit-тесты (без БД)

Цель: чистые функции и правила. Обязательные группы:
- `booking-engine`: рабочие интервалы, перерывы, исключения, генерация слотов, buffer, статусы, `any`, min notice/max advance, `occupiedKeys` (BOOKING_ENGINE_SPEC §13, кейсы 1–15);
- `permissions`: полнота таблицы роль×ключ; значения совпадают с PERMISSIONS_MATRIX (тест генерируется из константы и сверяется со снимком матрицы);
- `transitions`: статусы записи и платежа (все пары);
- `money`: целые minor units, форматирование, парсинг ввода;
- Zod-схемы: граничные значения, `.strict()` (лишние поля), нормализация телефона/email;
- `dedupeKey`, backoff, guard уведомлений; шаблоны писем (время в поясе бизнеса);
- `time`: локальное↔UTC, DST;
- `dashboard-math`: загрузка, дельты, границы периода;
- `tokens`: энтропия/формат, HMAC-хэш не равен токену.

## 3. Integration-тесты (реальная БД)

Среда: `MongoMemoryReplSet` (1 узел, `--replSet`), пересоздаётся на файл-набор; индексы создаются **теми же миграциями**, что и в production (тест проверяет, что миграции дают нужные индексы: `listIndexes`). Покрытие: репозитории (всегда с `ctx`), сервисы, транзакции, воркер уведомлений, дашборд-агрегации, миграции (применить с нуля, повторный запуск идемпотентен).

## 4. Business A vs Business B (обязательная изоляция)

**Фикстура:** два бизнеса с **пересекающимися** данными (одинаковые имена услуг, одинаковые телефоны клиентов, одинаковые даты/времена записей, разные таймзоны), в каждом — owner, admin, master, 2 сотрудника, 3 услуги, 5 клиентов, 10 записей, платежи, уведомления.

Проверки (каждая — автоматическая):
1. **Каждый `:id`-эндпоинт** (по реестру маршрутов, API_CONTRACTS §16): под сессией A запрос с id объекта B → `404` (не 403, не 200). Для `GET/PATCH/DELETE/POST-action`.
2. **Списки и поиск:** под A результаты `CUS-01`, `APT-01`, `PAY-01`, `STF-01`, `SVC-01`, `BLK-01`, `MEM-01`, `CAL-01` (и post-MVP `TRX-01`, `NTF-01`, `AUD-01` — после их появления) не содержат <!-- CHANGED: A3.5 --> ни одного объекта B (проверка по всем страницам); поиск по телефону клиента B → пусто.
3. **Агрегации:** `DSH-*` под A не меняются при добавлении данных в B (снимок до/после).
4. **Кросс-ссылки:** создание записи/платежа/привязки с `customerId|staffId|serviceId|appointmentId|staffIds|serviceIds` из B под сессией A → `404`, и **в БД ничего не создано** (проверка счётчиков).
5. **Подмена `businessId`:** в теле, query и заголовках (`X-Business-Id`) → `422`/игнор; фактическая запись — только в бизнес из сессии.
6. **Сессия:** отключённое членство (`MEM-03` или деактивация сотрудника `STF-04`) → мгновенная потеря доступа (следующий запрос `401/403`) и удалённые сессии; пользователь с членством в бизнесе A не может получить членство в B (уникальный индекс `userId`, `409 EMAIL_TAKEN`). Переключение `AUTH-05` на чужой бизнес → `404` — **post-MVP**. <!-- CHANGED: A3.5 -->
7. **Публичные эндпоинты:** slug A не отдаёт услуги/мастеров/слоты B; запись через slug A на `serviceId` B → `404`; токен управления из A не работает с данными B; неизвестный/неактивный slug → одинаковый `404`.
8. **Клиенты:** один телефон в A и B → две независимые записи; публичная запись в A не создаёт/не меняет клиента в B.
9. **Уникальность в разрезе бизнеса:** `slug` глобально, остальное (имя услуги, телефон клиента, `idempotencyKey`, `staffId` в `businessMembers`) — в рамках бизнеса.
10. **Tenant-guard:** прямой вызов модели без `businessId` в фильтре → `TenantGuardError` (unit над плагином для каждой бизнес-модели; список моделей берётся из реестра и сверяется с DATA_MODEL).
11. **Воркер уведомлений:** рендер использует данные бизнеса уведомления; письма A не содержат данных B.
12. **Аудит/журналы:** записи `auditLogs` A не видны B.
Негативный контроль: «мутант-тест» — временно убрать фильтр `businessId` в одном репозитории (в отдельной ветке/CI-джобе) и убедиться, что набор тестов падает.

## 5. Role-тесты

Таблица-драйвер генерируется из PERMISSIONS_MATRIX: для **каждого эндпоинта × каждой роли** ожидаемый результат (`200/201/204` | `403` | `404`-для-области `own`). Дополнительно:
- admin: нельзя менять admin/owner, `settings:business_write`, `settings:notifications_write`, `audit:read`, `members:invite_admin` → 403;
- master: нельзя `payments/transactions/dashboard/settings/members/audit/notifications` → 403; чужие записи/клиенты/календарь → 404; `PATCH` записи с любым полем кроме `visitNote` → 422; переходы статусов — только разрешённые; поля клиента ограничены (`email`, `notes`, `contacts` отсутствуют; `phone` зависит от `privacy.masterSeesCustomerPhone`);
- owner: единственный; нельзя отключить себя; передача владения (`MEM-05`) и создание/смена ролей admin — **post-MVP** (правила admin проверяются на уровне сервисов с фикстурой `world-ab`, где admin создан напрямую); <!-- CHANGED: A2b -->
- аутентификация: без cookie `401`; просроченная/удалённая сессия `401`; отключённый пользователь `401`.

## 6. API/contract-тесты

Реестр `defineRoute`: (а) множество ID в реестре = множеству **MVP-ID** (без пометки post-MVP) в API_CONTRACTS.md (парсится из документа; post-MVP ID в реестре отсутствуют); <!-- CHANGED: A3.5 --> (б) каждый маршрут: `ST-1` (401), `ST-2` (403 по матрице), `ST-3` (404 чужого), `ST-4` (strict-тело), `ST-5` (валидация), `ST-6` (rate limit для помеченных); (в) формат конверта успеха/ошибки; (г) коды из контракта; (д) DTO не содержат запрещённых полей (хэши, `occupiedKeys`, `bookingVersion`, `searchTokens`) — проверка через рекурсивный поиск по ключам; (е) `Cache-Control: no-store` на `/api/public/manage/*`; (ж) CSRF: мутация с чужим `Origin` → 403.

## 7. Гонки при записи (booking race)

Реальные параллельные запросы к Route Handler/сервису (Promise.all), реплика-сет:
1. 20 одновременных `PUB-06` на один слот → ровно один `201`, 19 × `409 SLOT_UNAVAILABLE`; в БД ровно одна активная запись; `occupiedKeys` уникальны.
2. Пересекающиеся (не совпадающие) интервалы: 10:00–11:00 и 10:30–11:30 одновременно → одна успешная.
3. «Любой мастер»: 3 запроса, 2 свободных мастера → 2 успеха у разных мастеров, 1 `409`.
4. Блок времени × запись на то же окно → не более одной успешной операции, нет записи внутри блока.
5. Перенос × создание в целевой слот → одна успешная операция.
6. Две параллельные отмены/смены статуса одной записи → одна успешная, вторая `409 INVALID_STATUS_TRANSITION`; `occupiedKeys` консистентны.
7. Повторяемость: каждый тест выполняется ≥ 20 итераций (цикл) в CI-джобе «race».
8. Проверка индекса: удалить unique-индекс `occupiedKeys` в тесте → тест №1 обязан падать (доказывает, что защиту даёт индекс, а не удача).

## 8. Часовые пояса и DST

Пояса: `Asia/Bishkek` (UTC+6, без DST), `Europe/Moscow`, `America/New_York` (DST 2026-03-08 и 2026-11-01), `Europe/Berlin` (2026-03-29, 2026-10-25), `Pacific/Auckland` (южное полушарие DST), `Asia/Kolkata` (UTC+5:30 — нецелое смещение). Для каждого: слоты дня перехода (пропущенный/повторяющийся час), границы периода дашборда, `dateTrunc` по дням, неделя в `CAL-01`, время в письмах («10:00 МСК»-подобная подпись зоны), напоминания «за 24 ч» через переход (абсолютные 24 часа, не «то же время вчера»), `maxAdvanceDays` на границе локальной полуночи. Тесты запускаются с `TZ` процесса, отличным от пояса бизнеса (`TZ=UTC` и `TZ=America/Los_Angeles`), чтобы выявить неявное использование локального пояса сервера.

## 9. Оплаты, уведомления, dashboard

Полные списки кейсов: PAYMENTS_SPEC §8, NOTIFICATIONS_SPEC §10, DASHBOARD_SPEC §7. Обязательная кросс-проверка (MVP): выручка из `DSH-01` = Σ(`charge`) − Σ(`refund`) по `transactions.occurredAt` периода (прямой запрос к БД в тесте); Σ `CUS-03.totalPaidMinor` по клиентам = Σ нетто-транзакций за **всё время** по тем же клиентам. `PAY-01 meta.totals` считается по платежам (по `paidAt`) и может расходиться с дашбордом при возврате в другом периоде — проверяется отдельным тестом (PAYMENTS_SPEC §5). Post-MVP добавляются: `TRX-01 meta.totals.netMinor` и Σ `DSH-02`. <!-- CHANGED: A2b -->

## 10. Безопасность

- **Сессии/cookie:** флаги `HttpOnly`, `SameSite=Lax`, `Secure` (production-конфиг); токен в БД только хэшем; ротация сессии при логине; удаление всех сессий при смене/сбросе пароля; абсолютный и скользящий сроки.
- **Пароли:** argon2id, не логируются; слабые пароли отклоняются; одинаковое время/ответ для неизвестного email (проверка статистически допустимой разницы в тесте с порогом).
- **Rate limiting:** каждая политика `RL-*` — тест на превышение (`429` + `Retry-After`) и на сброс окна (фейковые часы).
- **CSRF:** проверка `Origin/Referer` для мутаций; `Content-Type` ≠ JSON → 415.
- **Инъекции:** NoSQL-инъекция — тела вида `{ "email": { "$ne": null } }`, `phone: { $gt: "" }`, `q` с оператором → `422` (Zod принимает только строки); санитизация регулярных выражений в префиксном поиске (экранирование).
- **Mass assignment:** лишние поля (`role`, `status`, `businessId`, `createdBy`, `isDeleted`) → `422`.
- **Токены:** управления записью (энтропия 256 бит, одноразовость где применимо, срок), приглашения, сброса; неверные → единый `404`.
- **Утечки:** DTO без чувствительных полей (§6д); ошибки без стека; сообщения аутентификации без перечисления аккаунтов; `X-Powered-By` отключён; заголовки безопасности (`X-Content-Type-Options`, `Referrer-Policy`, `Content-Security-Policy` базовая, `Permissions-Policy`).
- **Публичные эндпоинты:** honeypot, лимиты, отсутствие данных клиентов в ответах.
- **Зависимости:** `npm audit` в CI (блокирует critical/high без исключения с обоснованием); версия Next.js — актуальная поддерживаемая (в текущем `package.json` 14.1.0 с известными уязвимостями, обновление — Этап 1).
- **Секреты:** сканер секретов в CI (например, gitleaks) по репозиторию и архиву.

## 11. Browser / E2E (Playwright)

Сквозные сценарии (на тестовой БД, `ConsoleEmailProvider`):
1. Регистрация бизнеса → онбординг → создание мастера, услуги, расписания.
2. Публичная запись: 5 шагов → подтверждение → письмо с ссылкой → отмена по ссылке.
3. Перенос по ссылке; конфликт слота при одновременной записи в двух вкладках.
4. Администратор: создание записи в календаре, перенос, статус «Завершена», приём оплаты, возврат.
5. Master: вход, «Мой день», завершение, заметка; отсутствие пунктов меню с деньгами; прямой URL чужого раздела → «Недостаточно прав»/404.
6. Dashboard (MVP): смена периода, 4 KPI и «Ближайшие записи», пустое состояние новой организации (график, загрузка, топ услуг, фильтр мастера — post-MVP). <!-- CHANGED: A3.5 -->
7. Изоляция в UI: два браузерных контекста (A и B); прямые URL объектов другого бизнеса → «Не найдено».
8. ~~Переключение между двумя бизнесами одного пользователя~~ — **post-MVP** (`AUTH-05`); в MVP вместо него: приглашённый master принимает приглашение (`STF-02` → письмо → `AUTH-06`), входит и видит только «Мой день». <!-- CHANGED: A3.5 -->
9. Мобильный viewport (375×812): публичная запись и календарь «День», нижняя навигация.
10. Клавиатурный проход публичной записи без мыши.

## 13. Фикстуры и тестовые данные

`tests/fixtures/`: `builders` (фабрики `buildBusiness`, `buildStaff`, `buildService`, `buildCustomer`, `buildAppointment`, `buildPayment`) с seed-генератором; `world-ab.ts` (§4); `dashboard-fixture.ts` (DASHBOARD_SPEC §7); `clock.ts` (фейковое время). Фабрики создают данные **через сервисы/репозитории**, а не вставкой в обход инвариантов (кроме специальных негативных тестов). Тестовые пароли/секреты — только тестовые константы. Каждый тест изолирован (очистка коллекций или отдельная БД на файл).

## 14. Команды (будут добавлены на Этапе 1)

`npm run lint` · `npm run typecheck` · `npm run test:unit` · `npm run test:integration` · `npm run test:api` · `npm run test:isolation` (набор §4) · `npm run test:race` (§7, циклы) · `npm run test:e2e` · `npm run test:a11y` · `npm run check:contrast` · `npm run migrate` · `npm run build` · `npm run check:docs` (проверка ID эндпоинтов/ключей прав между документами и реестром). ## 15. Definition of done для тестирования

Этап закрыт, если: (1) все тесты этапа зелёные в CI, (2) тесты изоляции A/B (§4) и ролей (§5) покрывают **все** эндпоинты этапа, (3) для доменной логики — тест на каждый пункт соответствующего документа, (4) нет пропущенных (`skip`) тестов, (5) для функций с конкуренцией — race-тест (§7), (6) время/пояс — DST-тест (§8), (7) критический пользовательский сценарий этапа покрыт E2E, (8) повторный запуск набора даёт те же результаты (нет флейков; флейковый тест чинится или удаляется до слияния), (9) отчёт этапа честно перечисляет невозможные проверки.
