## Этап 0. Спайк `occupiedKeys` (1–2 дня)

**Цель:** на реальном MongoDB 8.0 replica set доказать (или опровергнуть) механизм защиты от двойной записи (DATA_MODEL §17) до начала этапа 6.
**Исполнитель:** основной исполнитель готовит spike-скрипт и отчёт; запуск выполняется на MongoDB 8.0 replica set.
**Эндпоинты:** нет. **Модели:** временная коллекция `spikeAppointments` (удаляется после спайка).
**Что проверяется:**
1. Уникальный partial multikey-индекс `{occupiedKeys:1}` (`partialFilterExpression:{occupiedKeys:{$exists:true}}`) создаётся и работает на 8.0.
2. 1 000 итераций × 20 параллельных вставок одного слота → ровно одна успешная в каждой итерации.
3. Пересекающиеся, но не совпадающие интервалы (10:00–11:00 и 10:30–11:30) → вторая отвергается (`E11000`).
4. Документы без поля `occupiedKeys` (отменённые, `$unset`) не конфликтуют между собой (тысячи документов).
5. Перенос единичным `updateOne` при конфликте: старое время и ключи остаются нетронутыми.
6. Максимальная запись (720 мин + буфер 120 мин → 168 ключей): время вставки, размер индекса на 100 000 записей.
7. Транзакция с `$inc` по документу `staff` + вставка записи: конкурентные транзакции дают write-conflict/повтор, итог консистентен.
8. Совместимость выбранных версий драйвера/Mongoose с MongoDB 8.0 (транзакции, `$dateTrunc`).
**Готово, когда:** отчёт `docs/spikes/OCCUPIED_KEYS_REPORT.md` с цифрами и решением **go / no-go**; при no-go — предложенная альтернатива (lock-документы по мастеру/дню, DATA_MODEL §17 «отвергнуто (b)») и обновление документов **до** этапа 6.
**Тесты:** сам скрипт (повторяемый, с seed).
