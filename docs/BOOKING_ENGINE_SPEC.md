# BOOKING_ENGINE_SPEC.md — Движок доступности и записи

Из reference-проекта (Easy!Appointments) использованы **только идеи**: порядок вычитания периодов, «исключение заменяет день», пересечение интервалов, окно предварительной записи, токен-ссылка для отмены. Код не копируется и не открывается при реализации (ADR-012, лицензия GPL-3.0). Всё поведение определено здесь и проверяется тестами.

## 1. Структура модуля

```
src/server/domain/booking-engine/
  time.ts             — конвертации локальное↔UTC (luxon), DST-безопасные
  working-hours.ts    — computeWorkingIntervals(staff, localDate)   (чистая)
  slots.ts            — generateSlots(...)                           (чистая)
  availability.ts     — getAvailability(...), isSlotAvailable(...)   (чистая)
  occupancy.ts        — occupiedKeysFor(staffId, start, blockedUntil)(чистая)
  transitions.ts      — таблица допустимых статусов                  (чистая)
src/server/services/booking-service.ts — I/O: загрузка данных, транзакции, запись
```
Чистые функции не обращаются к БД и времени (`now` передаётся параметром) — полностью unit-тестируемы.

## 2. Время и часовой пояс

- Источник правды о локальном времени — `businesses.timezone` (IANA). Расписание, исключения, «сегодня», `maxAdvanceDays`, дашборд — в **часовом поясе бизнеса**.
- Хранение моментов — UTC (`Date`). Локальные даты (`YYYY-MM-DD`) и время суток (`HH:mm`) хранятся только там, где они — часть правила (расписание, исключения).
- API принимает/отдаёт моменты как ISO 8601 UTC с `Z`; публичный UI показывает время **в поясе бизнеса** (с подписью зоны), не в поясе браузера.
- Длительности считаются в **абсолютных минутах** (UTC), не как разность настенных часов.

## 3. Входные данные для расчёта

Для сотрудника и локальной даты `D` движок получает: `staffSchedules.weekly`, `staffExceptions` на `D`, `blockedPeriods`, пересекающие сутки `D` (расширенные на ±1 день для DST), активные `appointments` мастера в окне, `service` (длительность, buffer), `settings.booking`, `now`, `business.timezone`.

## 4. Алгоритм `computeWorkingIntervals(staff, D)`

1. Если у сотрудника есть `staffExceptions` на `D`:
   - `day_off` → рабочих интервалов нет;
   - `custom` → берутся его `intervals` и `breaks` (рабочий план недели **полностью игнорируется**).
2. Иначе берётся запись `weekly` с `isoWeekday(D)`; нет записи → выходной.
3. Каждый интервал `[start,end)` (локальные `HH:mm`) переводится в UTC (см. §10 DST); из интервалов вычитаются перерывы → список рабочих отрезков `W` (UTC).

## 5. Алгоритм `generateSlots(service, W, step, now, rules)`

Для каждого отрезка `w = [ws, we)` из `W`:
1. Кандидаты: `t = ws, ws+step, ws+2·step …` (**сетка привязана к началу отрезка**; `step = settings.booking.slotStepMinutes`).
2. Кандидат допустим, если **услуга целиком** `[t, t+duration)` лежит внутри `w` (т.е. `t+duration ≤ we`). Buffer может выходить за конец отрезка/смены — buffer не обязан попадать в рабочее время.
3. Занятый диапазон кандидата: `O(t) = [t, t+duration+buffer)`.
4. Кандидат отбрасывается, если `O(t)` пересекается с занятым диапазоном существующей активной записи `[a.startAt, a.blockedUntilAt)` **или** с любым `blockedPeriod` мастера.
   Пересечение полуинтервалов: `A.start < B.end AND A.end > B.start`.
5. Если действуют публичные правила (`rules.enforceNotice = true`):
   - `t ≥ now + minNoticeMinutes`;
   - локальная дата `t` ≤ локальная «сегодня» + `maxAdvanceDays`.
   Owner/admin при внутренней записи могут передать `enforceNotice=false` (но не нарушают занятость).
6. Результат — отсортированный список `startAt` (UTC).

Учитываемые статусы записей: `pending`, `confirmed`, `completed` **занимают** время; `cancelled`, `no_show` — нет.

## 6. «Любой мастер» (`staffId = "any"`)

1. Кандидаты-мастера: `isActive`, `acceptsOnlineBooking`, привязаны к услуге (`staffServices`), не удалены.
2. Для каждого считается `generateSlots`. Публичный ответ — **объединение** стартов (уникальные `startAt`), без раскрытия, кто именно свободен.
3. При создании записи на `any` сервис выбирает мастера по порядку: (a) меньше всего записей на этот локальный день (балансировка), (b) меньший `displayOrder`, (c) меньший `_id`. Если вставка падает на `E11000` (гонка) — пробует следующего кандидата; если все заняты — `409 SLOT_UNAVAILABLE`.
4. В подтверждении клиенту показывается назначенный мастер.

## 7. Создание записи (`createAppointment`)

Вход: `serviceId`, `staffId|any`, `startAt`, данные клиента, `source`, `Idempotency-Key`.

1. Контекст бизнеса — из слага (публично) или сессии (внутренне). Загрузить `business`, `settings`, `service` (active, `onlineBookingEnabled` для публичной), `staff` — **все с `businessId` контекста**; иначе `404`.
2. Проверить `staffServices(staff, service)`; иначе `422 STAFF_DOES_NOT_PROVIDE_SERVICE`.
3. `startAt` кратен 5 мин и ровно попадает в сетку слотов этого мастера (`isSlotAvailable`) — иначе `409 SLOT_UNAVAILABLE`.
4. Идемпотентность: если `(businessId, idempotencyKey)` уже есть → вернуть существующую запись `200` (тот же ответ), новую не создавать.
5. Mongo-транзакция (до 3 повторов при `TransientTransactionError`):
   1. `$inc staff.bookingVersion` (сериализация с изменением расписания/блокировок);
   2. повторить проверку блокировок и рабочего времени внутри транзакции;
   3. найти клиента по `(businessId, phoneNormalized)`; нет — создать (`source: public|internal`). **Существующего клиента публичная запись не изменяет** (не перезаписывает имя/email/заметки; если у клиента пуст email — допускается заполнить). Данные клиента в ответе не раскрываются;
   4. вставить `appointments` со `serviceSnapshot`, `endAt`, `blockedUntilAt`, `occupiedKeys`, `contactEmail`, `manageTokenHash` (если нужен), статус: `confirmed` при `autoConfirm` (или внутренней записи), иначе `pending`;
   5. поставить в очередь уведомления: при статусе `confirmed` — `appointment_confirmed` и напоминания; при `pending` — ничего до подтверждения (NOTIFICATIONS_SPEC §3–4);
   6. commit.
6. `E11000` по `occupiedKeys` → `409 SLOT_UNAVAILABLE` (для `any` — следующий кандидат).
7. Ответ: публичное представление записи; `manageToken` (открытый токен) возвращается **один раз** в ответе и письмом.

## 8. Защита от гонки

Три слоя, описанные в DATA_MODEL_MONGODB §17: (1) уникальный partial-индекс по `occupiedKeys` — жёсткий запрет пересечений; (2) транзакция + `$inc staff.bookingVersion`; (3) предварительная проверка. Инвариант: **для одного мастера не существует двух активных записей с пересекающимися `[startAt, blockedUntilAt)`**.
Блокировка времени (`createBlockedPeriod`): транзакция → `$inc staff.bookingVersion` → поиск активных записей, пересекающих `[startAt,endAt)` → если есть, `409 BLOCK_CONFLICTS_WITH_APPOINTMENTS` → вставка. Изменение расписания/исключений: транзакция с тем же `$inc`; будущие записи, оказавшиеся вне нового расписания, **не отменяются** автоматически — ответ возвращает `affectedAppointmentsCount` для предупреждения.

## 9. Статусы и переходы

| Из \ В | pending | confirmed | completed | cancelled | no_show |
|---|---|---|---|---|---|
| pending | — | owner/admin/master | owner/admin | owner/admin/master/клиент | owner/admin |
| confirmed | — | — | owner/admin/master | owner/admin/master/клиент | owner/admin/master |
| completed | — | owner/admin (откат) | — | — | — |
| cancelled | — | owner/admin (восстановление, если слот свободен) | — | — | — |
| no_show | — | owner/admin (откат) | owner/admin | — | — |

Дополнительно: `completed` и `no_show` допустимы только если `startAt ≤ now` (нельзя завершить будущую запись). Побочные эффекты:
- → `cancelled`/`no_show`: `$unset occupiedKeys`, `cancelledAt/By/Reason`, отменить запланированные уведомления, поставить `appointment_cancelled` (только для `cancelled`);
- ← восстановление в активный статус: заново проставить `occupiedKeys` (может дать `409`);
- → `completed`: `completedAt`, поставить `followup_after_visit`;
- любое изменение времени: отменить старые напоминания, создать новые.

## 10. DST и аномалии времени

| Ситуация | Правило |
|---|---|
| Локальное время не существует (весна, «пропущенный» час) | Кандидат пропускается: проверка «локальное→UTC→локальное» должна вернуть то же `HH:mm`, иначе слот невалиден |
| Локальное время неоднозначно (осень, повторяющийся час) | Берётся **первое** вхождение (раннее смещение); второе не генерируется |
| День длиной 23 или 25 часов | Нагрузка считается по абсолютным минутам; сетка слотов привязана к началу отрезка, поэтому не «ломается» |
| Расписание «09:00–18:00» в день перевода | Границы отрезка переводятся через `DateTime.fromObject({...}, {zone})`; длительность отрезка может отличаться на 60 минут от «обычной» — это корректно |
| Бизнес без DST (Бишкек, Москва) | Те же алгоритмы, DST-ветви просто не срабатывают |

## 11. Отмена и перенос клиентом (публичные, по токену)

**Токен:** 32 случайных байта (`crypto.randomBytes`), base64url, 256 бит. В БД только `HMAC-SHA256(token, TOKEN_PEPPER)`. Ссылка: `APP_BASE_URL/b/{slug}/manage/{token}`; страница отдаёт `Referrer-Policy: no-referrer`, `Cache-Control: no-store`. Токен действителен до `startAt + 24 ч` (`manageTokenExpiresAt`). Неверный/истёкший токен → единый `404`.

**Отмена:** разрешена, если статус `pending|confirmed` и `now ≤ startAt − cancellationWindowHours`; иначе `403 CANCELLATION_WINDOW_PASSED`. Эффекты — как в §9.
**Перенос:** те же условия + `rescheduleCount < customerRescheduleLimit` (иначе `403 RESCHEDULE_LIMIT_REACHED`). Услуга и мастер **сохраняются** (если у записи был «any» — остаётся назначенный мастер). Слоты считаются с исключением переносимой записи из занятости; новое время проверяется по тем же правилам и обновляется единичным `updateOne` (слой 1). После переноса: `rescheduleCount+1`, `manageTokenExpiresAt` пересчитывается, старые напоминания отменяются, ставится `appointment_changed` и новые напоминания.
Перенос/отмена клиентом пишутся в аудит как `actorRole: customer`.

## 12. Внутренняя запись и перенос (owner/admin)

Те же функции, но (а) `enforceNotice` можно отключить; (б) `confirm=true` статус сразу; (в) клиент выбирается/создаётся явно; (г) перенос не ограничен `customerRescheduleLimit`, не увеличивает `rescheduleCount`.

## 13. Тест-кейсы (обязательный минимум)

Unit (чистые функции):
1. Простой день 09:00–18:00, услуга 60 мин, шаг 30 → ожидаемые слоты 09:00…17:00.
2. Перерыв 13:00–14:00 → нет слотов, пересекающих перерыв; слот 12:00 с услугой 60 мин допустим, 12:30 — нет.
3. Исключение `day_off` → пусто; `custom` заменяет недельный план полностью.
4. Блокировка 15:00–16:00 → слоты, пересекающие её, отсутствуют.
5. Buffer 15 мин: существующая запись 10:00–11:00 + buffer → следующий допустимый старт 11:15 (шаг 15).
6. Buffer после последней записи может выходить за конец смены; услуга — нет.
7. Услуга длиннее любого окна → пусто.
8. Статусы: `cancelled`/`no_show` освобождают слот; `pending`/`confirmed`/`completed` занимают.
9. `minNoticeMinutes`, `maxAdvanceDays` (граница включительно/исключительно).
10. «Любой мастер»: объединение слотов; детерминированный выбор мастера; пересечение с другим мастером не мешает.
11. DST `America/New_York` 2026-03-08 (пропуск 02:00–03:00): слот 02:30 отсутствует; день содержит корректное число слотов. 2026-11-01 (повтор 01:00–02:00): 01:30 генерируется один раз.
12. DST `Europe/Berlin` 2026-03-29 и 2026-10-25 — аналогично; `Asia/Bishkek` (без DST) — стабильность.
13. Бизнес в UTC+6, клиент в другом поясе: слот «10:00» всегда отображается как 10:00 бизнеса.
14. Неповторяемость ключей: `occupiedKeys` для записи 10:00+60+15 → 15 ключей по 5 мин; соседние записи без пересечения дают непересекающиеся наборы.
15. Таблица переходов: каждая недопустимая пара → ошибка `409 INVALID_STATUS_TRANSITION`.

Integration (реальный replica set):
16. 20 параллельных `POST` на один слот → ровно один `201`, остальные `409 SLOT_UNAVAILABLE`.
17. Параллельно «any master» при 2 свободных мастерах и 3 запросах → две успешные записи у разных мастеров, одна `409`.
18. Параллельные: создание блокировки и запись на то же время → не более одной успешной операции.
19. Перенос в занятый слот → `409`, старое время сохранено, `occupiedKeys` не изменились.
20. Отмена освобождает слот: сразу после отмены такая же запись создаётся успешно.
21. Идемпотентность: повтор с тем же `Idempotency-Key` не создаёт вторую запись.
22. Запись на услугу/мастера другого бизнеса → `404`; клиент из бизнеса B не находится/не смешивается в A.
23. Публичная запись не изменяет имя/заметки существующего клиента.
24. Токен: неверный, истёкший, от чужой записи → `404`; окно отмены; лимит переносов.
25. Изменение расписания с будущими записями → ответ с `affectedAppointmentsCount`, записи не отменены.
