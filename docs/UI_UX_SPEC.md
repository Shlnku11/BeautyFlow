# UI_UX_SPEC.md — Экраны, потоки, состояния

Язык интерфейса — русский (ключи словаря, не хардкод: CODING_STANDARDS §12). Визуальные токены — DESIGN_SYSTEM.md. Каждый экран ссылается на **ID эндпоинтов** из API_CONTRACTS.md. UI **не обращается к БД** и не вызывает ничего, кроме API.

**Post-MVP экраны (убраны из sitemap, не реализуются в MVP):** `/app/transactions` (TRX-01/02), `/app/notifications` (NTF-01/02), `/app/audit-log` (AUD-01), вкладка «Уведомления» в настройках (SET-04), переключение бизнеса (AUTH-05), смена имени профиля (AUTH-10). Журнал уведомлений в БД ведётся, но в MVP в интерфейсе не показывается; история денег в MVP — список оплат (`PAY-01`).
Существующие страницы прототипа `/` (мастер записи) и `/submissions` **удаляются** на Этапе 11 после появления реальных аналогов; до этого не используются как основа.
Маршрутизация: React Router v7 задаёт SPA routes и UX-guards (redirect to `/login` без сессии); **безопасность обеспечивается Express API**. Навигация скрывает недоступное по `AUTH-04.permissions`, но сервер проверяет всегда.

## 2. Общий каркас приложения

Реализуется как React SPA на Vite с React Router v7: route tree воспроизводит sitemap ниже, включая dynamic params `:slug`, `:id`, `:token`; серверный fallback для deep links отдаёт SPA entry. Все сетевые запросы идут к существующим путям `/api/**` через api-client.

Desktop ≥1024px: sidebar 264px (стекло) · topbar 64px (стекло; название бизнеса (без переключателя — в MVP один бизнес на пользователя), глобальный поиск клиентов `CUS-01`, кнопка «＋ Запись» `APT-02`, меню пользователя) · контент max-width 1440px на плотных поверхностях.
Tablet 768–1023px: свёрнутый sidebar 72px. Mobile <768px: topbar 56px + нижняя навигация (DESIGN_SYSTEM §6) + FAB «＋ Запись» (только owner/admin).
Пункты навигации: **owner/admin:** Обзор · Календарь · Клиенты · Сотрудники · Услуги · Оплаты · Настройки. **master:** Мой день · Календарь · Клиенты. Нижняя панель mobile: Обзор/Мой день · Календарь · Клиенты · ＋ · Ещё.

## 3. Экраны

Формат: **Назначение · Layout · Данные (API) · Действия · Права**.

### 3.1 Login `/login` · Register `/register`
- **Login:** карточка (стекло) по центру: email, пароль (кнопка «показать»), «Забыли пароль?», «Войти». API: `AUTH-02`. После входа — переход в `/app` (в MVP у пользователя один бизнес; экрана выбора бизнеса нет). Ошибки: общий «Неверный email или пароль» (без деталей) под формой; блокировка по лимиту — текст с временем ожидания.
- **Register:** шаги в одной форме (2 секции): «Бизнес» (название, адрес-ссылка `slug` с предпросмотром `domain/b/slug`, часовой пояс — автоопределение Intl + select, валюта, **страна `countryCode` — select (RU, KZ, KG, US, Другая=OTHER); по умолчанию подставляется регион локали браузера (Intl), иначе значение из `APP_DEFAULT_COUNTRY_CODE`; если определить нельзя — обязательный выбор без значения по умолчанию; подсказка: «Страна определяет разбор телефонов клиентов»**) <!-- CHANGED: A3 --> и «Владелец» (имя, email, пароль с подсказкой требований, чекбокс принятия условий). API: `AUTH-01`. После успеха — онбординг (§3.3 пустое состояние). Honeypot скрыт от скринридеров (`aria-hidden`, `tabindex=-1`).
- **Forgot/Reset/Accept-invite:** одно поле/пара полей, `AUTH-07/08/06`; ответ на forgot всегда «Если аккаунт существует, мы отправили письмо».

### 3.2 Публичная запись `/b/[slug]`
Поток (шаги с индикатором «Шаг N из 5», кнопка «Назад» без потери данных; состояние хранится в URL-параметрах/памяти формы, **не** в localStorage с персональными данными):
1. **Услуга** — карточки услуг (название, длительность, цена). `PUB-01`, `PUB-02`.
2. **Мастер** — карточки + «Любой мастер» (по умолчанию). `PUB-03`.
3. **Дата** — календарь месяца: доступные дни активны, остальные неактивны с текстовым пояснением; ≤ `maxAdvanceDays`. `PUB-05`.
4. **Время** — сетка слотов выбранной даты (время в поясе бизнеса с подписью зоны), группировка «Утро/День/Вечер». `PUB-04`. Нет слотов → пустое состояние «На эту дату нет свободного времени» + кнопка «Ближайшая доступная дата» (по `PUB-05`).
5. **Контакты и подтверждение** — имя, фамилия (опц.), телефон, email, комментарий, чекбокс согласия с обработкой данных (**показывается только если `PUB-01.consent.required`; рядом — `consent.text`, при пустом тексте — стандартный текст из словаря**), сводка (услуга, мастер, дата/время, цена). `PUB-06`. Конфликт `409 SLOT_UNAVAILABLE` → сообщение «Это время только что заняли», возврат к шагу 4 с обновлёнными слотами; введённые контакты сохраняются.
6. **Подтверждение** — «Запись создана» (или «Заявка отправлена, мастер подтвердит» при `pending`), сводка, кнопки «Добавить в календарь» (ссылки Google/Outlook, из прототипа), «Управлять записью» (ссылка `manageUrl`). Письмо с той же ссылкой отправляется.
Layout: hero-карточка (стекло) с названием бизнеса, адресом, телефоном; шаги — плотные карточки; mobile-first (одна колонка, липкая кнопка «Далее» внизу). Ошибки валидации — инлайн; `429` — «Слишком много попыток, попробуйте позже».

### 3.3 Управление записью клиентом `/b/[slug]/manage/[token]`
Показывает запись (`PUB-07`), кнопки «Перенести» (→ выбор даты/времени через `PUB-08`, подтверждение `PUB-10`) и «Отменить» (`PUB-09`, диалог подтверждения с полем причины). Если окно отмены прошло/лимит переносов исчерпан — кнопки неактивны с пояснением и телефоном бизнеса. Неверная ссылка → нейтральная страница «Ссылка недействительна».

### 3.4 Dashboard владельца `/app/dashboard` (owner, admin)
<!-- CHANGED: A3 -->
**MVP-версия (минимальная):** Layout: фильтр периода (`today/week/month/last_month` или даты) → **4 KPI-карточки** (стекло): выручка нетто · записи (всего) · отмены + no_show (число и доля) · новые клиенты → блок «Ближайшие записи». API: `DSH-01`, `DSH-05` (независимые запросы, свои skeleton/ошибки). Без сравнения с прошлым периодом, без фильтра по мастеру в UI. График выручки, загрузка мастеров, топ услуг — post-MVP (`DSH-02/03/04`). Действия: клик по записи → панель записи (§3.6); «Принять оплату» из пустых состояний. **Admin** видит тот же экран; ссылки на owner-only разделы отсутствуют. Пустая организация: онбординг-чек-лист (мастер → услуги → расписание → ссылка на запись; прогресс считается по `STF-01`, `SVC-01`, `STF-06`).

### 3.5 Мой день `/app/my-day` (master)
Список записей на выбранную дату (по умолчанию сегодня) с временем, клиентом (имя, телефон если разрешено), услугой, статусом; блок «Ближайшие 7 дней»; счётчики месяца (без денег). Быстрые действия на карточке: «Подтвердить», «Завершить», «Не пришёл», «Отменить» (с причиной), «Заметка после визита». API: `MST-01`, `APT-06`, `APT-04` (`visitNote`). Нет доступа к деньгам/настройкам.

### 3.6 Календарь `/app/calendar`
Layout: панель управления (переключатель День/Неделя, навигация ◀ Сегодня ▶, выбор даты, фильтр мастеров — мультиселект с цветами; master — без фильтра) · сетка: день — колонки по мастерам, неделя — колонки по дням (при нескольких мастерах — один выбранный мастер или режим «Все» со свёрнутыми событиями); ось времени по рабочим часам бизнеса (минимум 08:00–21:00, расширяется по данным); шаг сетки 15 мин; нерабочее время закрашено; блокировки штрихованы; линия «сейчас»; справа/снизу — индикатор загрузки мастера (`CAL-01.load`).
Данные: `CAL-01`. Действия (owner/admin): клик по пустому слоту → «Новая запись» (предзаполнены мастер/время; `AVL-01`, `APT-02`); клик по записи → панель записи (детали, статусы `APT-06`, перенос `APT-05` через выбор слота `AVL-01`, заметки `APT-04`, оплата: остаток берётся из `APT-03` (`payment.balanceMinor`), принять оплату — `PAY-02`); «Заблокировать время» (`BLK-02`), удалить блок (`BLK-03`). **Drag-and-drop** переноса — не в MVP (перенос через диалог — доступнее). Master: только просмотр своих записей и смена статуса/заметка. Mobile: вид «День» + переключатель мастера; неделя — как список по дням. Альтернатива для доступности: кнопка «Список записей» (`APT-01`).

### 3.7 Клиенты `/app/customers`
Таблица (mobile — карточки): имя, телефон, email, визитов, последний визит, следующий визит; поиск (debounce 300 мс, ≥2 символов), фильтр «есть будущие записи», сортировка, пагинация. «＋ Клиент» (`CUS-02`) — диалог формы. API: `CUS-01`. **Master:** видит имя и телефон (если разрешено), без email/визитов-итогов.
### 3.8 Карточка клиента `/app/customers/[id]`
Шапка: имя, контакты (телефон/email/другие), кнопки «Записать» (`APT-02` с `customerId`), «Изменить» (`CUS-04`); удаления клиента в MVP нет (`CUS-05` — post-MVP). Блок summary (визитов, последний/следующий, сумма оплат — `CUS-03`). Вкладки: **История записей** (`CUS-06`), **Заметки** (поле `notes`, автосохранение нет — явная кнопка «Сохранить», `CUS-04`), **Оплаты** (`PAY-01?customerId`, только owner/admin). Master: имя, телефон, его визиты и `visitNote`.

### 3.9 Сотрудники `/app/staff`, `/app/staff/[id]`
Список: аватар-цвет, имя, статус (активен/неактивен), услуги (кол-во), «принимает онлайн-запись». `STF-01`, «＋ Сотрудник» `STF-02` (форма: имя, цвет, телефон, **email — если указан, на него уходит приглашение в систему с ролью master**; подсказка под полем; результат `accessInvite`). Удаления сотрудника нет (`STF-05` — post-MVP): только деактивация. Карточка — вкладки: **Профиль** (`STF-03/04`; деактивация с подтверждением и предупреждением о будущих записях `STF-04 confirm`), **Расписание** (`STF-06/07`: 7 строк дней, переключатель «рабочий», интервалы (до 3), перерывы; ошибки пересечений инлайн; после сохранения показывается `affectedAppointmentsCount`), **Исключения** (`STF-08/09/10`: список + форма «Выходной/Особый день»), **Услуги** (`STF-11/12`: чекбоксы услуг), **Доступ** (`MEM-01`, `MEM-03`, `MEM-04`: статус членства (приглашён/активен/отключён), «Отправить приглашение повторно», «Отключить/Включить доступ»; первичное приглашение создаётся при создании сотрудника с email — `STF-02`; доступно owner/admin) <!-- CHANGED: A3 -->. Блокировки времени — в календаре (`BLK-*`). Master: только своя вкладка «Профиль/Расписание» read-only.

### 3.10 Услуги `/app/services`
Таблица: название, длительность, buffer, цена, мастера, онлайн, активна. `SVC-01`, `SVC-02`, `SVC-04`. Форма услуги в диалоге: название, описание, длительность (select кратно 5), buffer, цена (поле денег с валютой бизнеса), мастера (чекбоксы), «Доступна онлайн», «Активна». Удаления нет (`SVC-05` — post-MVP): услуга скрывается переключателем «Активна» (`SVC-04`). <!-- CHANGED: A3 -->

### 3.11 Оплаты `/app/payments`
<!-- CHANGED: A3 -->
- **Оплаты:** фильтры (период, метод, статус, мастер, поиск клиента), таблица (дата, клиент, запись, метод, сумма, возвращено, статус, принял), итоги над таблицей (`meta.totals`), «＋ Принять оплату» (`PAY-02`) — **упрощённая форма:** запись (поиск), сумма (предзаполнена остатком из `APT-03` → `payment.balanceMinor`), метод (cash/card/transfer/online), заметка; **статус — select «Оплачено» (по умолчанию) / «Ожидает оплаты»** (иначе платёж `pending` не мог бы возникнуть, и действия `PAY-04`/`PAY-05` были бы недостижимы) <!-- CHANGED: A2b -->; дата оплаты = текущий момент (поле даты в MVP-форме не показывается); действия строки: «Отметить оплаченной» для `pending` (`PAY-04`), «Отменить» для `pending` (`PAY-05`), «Вернуть» для `paid` (`PAY-06`, диалог с суммой и обязательной причиной). API: `PAY-01`, `PAY-02`, `PAY-04`, `PAY-05`, `PAY-06`. Карточки платежа нет (`PAY-03` — post-MVP): данные в строке/раскрывающейся панели.
- **Транзакции:** экран и журнал (`TRX-01/02`) — **post-MVP**; в MVP «историей транзакций» служит этот список оплат (фильтры период/метод/статус/мастер/клиент, кто принял оплату, переход к записи).

### 3.12 Уведомления — **post-MVP** <!-- CHANGED: A3 -->

### 3.13 Настройки `/app/settings`
Вкладки: **Бизнес** (`SET-01/02`; owner редактирует, admin видит read-only; slug показан, неизменяем; смена timezone/currency — с предупреждением и обработкой `409`; поле «Страна» (`countryCode`) с подсказкой «не пересчитывает уже сохранённые телефоны»; блок «Конфиденциальность»: `masterSeesCustomerPhone`, `requireConsent`, `consentText` (текст согласия для публичной записи), `dataRetentionDays` с подписью «пока не применяется автоматически»), **Запись** (`SET-03`: онлайн-запись вкл/выкл, шаг слотов, минимальное время до записи, горизонт (дни), автоподтверждение, окно отмены, лимит переносов; публичная ссылка с кнопкой «Скопировать» и QR — вне MVP), **Команда** (`MEM-01`, `MEM-03`, `MEM-04`: таблица членов, статус, повторное приглашение, отключение/включение; приглашение создаётся в «Сотрудники» — `STF-02`; смена ролей и передача владения — post-MVP). Вкладка «Уведомления» (`SET-04`) — post-MVP. <!-- CHANGED: A3 -->

## 4. Состояния (единые для всех экранов)

| Состояние | Правило |
|---|---|
| **Loading** | Skeleton той же геометрии (не спиннер на всю страницу); кнопки действий — loading-состояние; список > 300 мс → skeleton |
| **Empty** | Иллюстрация-иконка + заголовок + пояснение + главное действие (по правам). Пример: «Клиентов пока нет — добавьте первого». Пустой результат поиска/фильтра отличается от «данных нет» и предлагает «Сбросить фильтры» |
| **Error** | Блок с понятным текстом (карта кодов → русские сообщения), кнопка «Повторить», `requestId` мелким шрифтом для поддержки; 401 → редирект на `/login` с возвратом; 403 → экран «Недостаточно прав»; 404 → «Не найдено» (одинаково для чужого объекта); 429 → «Слишком часто, подождите N секунд»; 5xx → общий текст без технических деталей |
| **Success** | Toast `role="status"` («Запись создана», «Оплата принята»), для крупных действий — экран подтверждения (публичная запись) |
| **Confirmation** | Деструктивные/необратимые действия: диалог `alertdialog` с названием объекта и последствиями, кнопка действия именована глаголом («Отменить запись», «Вернуть 1 500 ₽»), фокус по умолчанию на «Отмена»; для крайне критичных (передача владения, возврат) — ввод пароля/причины |
| **Offline/сбой сети** | Баннер «Нет соединения», данные формы сохраняются, повтор вручную |

Дополнительно: оптимистичные обновления **не** используются для денег и записей (только после ответа сервера); при `409 SLOT_UNAVAILABLE`/конфликте версий — понятное сообщение и перезагрузка данных.

## 5. Формы

- Валидация: те же Zod-схемы (из `src/shared/schemas`), что на сервере; ошибки показываются при blur и при submit; серверный `422 details` отображается у полей.
- Один первичный CTA на форму; повторная отправка блокируется до ответа; `Idempotency-Key` создаётся на уровне формы для `PUB-06`, `APT-02`, `PAY-02`.
- Поля: видимые label, `autocomplete` (`name`, `tel`, `email`, `new-password`/`current-password`), `inputMode`; деньги вводятся в основных единицах, отправляются как `amountMinor` (преобразование в одном хелпере, без float-арифметики).
- Несохранённые изменения: при уходе — подтверждение.
- Телефон: ввод свободный, нормализация на сервере; отображение отформатированное.
- Время/даты: пикеры доступны с клавиатуры, формат `ДД.ММ.ГГГГ`, `ЧЧ:ММ` (24ч).
- **Стилизация — только Tailwind-классы по DESIGN_SYSTEM.** Никаких `.css`/`.module.css`, styled-components, CSS-in-JS и inline-стилей; единственный файл со стилями — `src/styles/tokens.css` (CSS-переменные токенов, DESIGN_SYSTEM §2) и директивы Tailwind. <!-- CHANGED: A3 -->

## 6. Адаптивность (breakpoints)

`sm` 640 · `md` 768 · `lg` 1024 · `xl` 1280 · `2xl` 1536 (стандартные Tailwind). Поведение: <768 нижняя навигация, таблицы → карточки, диалоги → bottom sheet, календарь «День»; 768–1023 свёрнутый sidebar; ≥1024 полный sidebar. Проверка на 320, 375, 768, 1024, 1440 px. Нет горизонтального скролла страницы ни на одной ширине.

## 7. Клавиатура и доступность

Skip-link; логичный Tab-порядок; `Esc` закрывает диалоги/меню; стрелки — в меню, списках выбора, сетке слотов (roving tabindex) и календаре; `Enter/Space` активируют; горячие клавиши не обязательны (если добавляются — `?` показывает список, отключаются в полях ввода). Сетка слотов — `radiogroup` со стрелочной навигацией. Календарь записей: `role="grid"` + альтернативный «Список записей». Динамические сообщения — `aria-live`. Заголовки h1–h3 без пропусков уровней, один h1 на экран. Проверки — DESIGN_SYSTEM §9.
