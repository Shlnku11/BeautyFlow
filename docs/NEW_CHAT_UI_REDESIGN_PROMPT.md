# BeautyFlow — аудит редизайна и промт для продолжения

## Аудит перед редизайном

**Продукт:** BeautyFlow, CRM для beauty-бизнеса: онлайн-запись, календарь команды, клиенты, услуги, сотрудники, оплаты, настройки и аналитика. Клиентская часть — React 19, TypeScript, Vite, React Router и Tailwind.

**Найденные проблемы до правок:**

### Критичные

1. Общий `a:hover` перекрашивал любой `<a>` в фиолетовый, включая CTA-ссылки с белым текстом. На залитой кнопке текст терял контраст.
2. Светлая и тёмная темы расходились между токенами `packages/client/src/styles/tokens.css` и HSL-переменными `packages/client/src/index.css`; границы контролов были слишком бледными.
3. Сетка календаря собирала рабочее, нерабочее и заблокированное время из `bg-neutral-*`. В тёмной теме эти классы превращались в чередующиеся почти чёрные ячейки.
4. Demo URL в README расходился с реальным slug в seed/API: старое `/b/beautyflow-demo` давало 404, рабочий slug — `/b/demo-salon`.

### Средние

1. Landing был простой длинной текстовой страницей без выраженной иерархии и убедительного продуктового примера.
2. Auth-экраны были изолированной карточкой на пустом фоне; общая оболочка иерархически не связывала вход, регистрацию и восстановление.
3. CRM-разделы использовали одни и те же плотные нейтральные таблицы, но не имели сильной общей визуальной системы; настройки оставляли много неструктурированного пространства.
4. Уведомления были ссылкой на список записей, а не оформленным состоянием/центром уведомлений.
5. Для анимаций не было общей сдержанной системы, проверки `prefers-reduced-motion` и явного разделения по назначению.

### Небольшие

1. Не хватало чёткой шкалы отступов, радиусов, состояния фокуса, hover/pressed и ясного различия поверхностей.
2. Публичная запись, списки, диалоги и уведомления были оформлены разными наборами похожих CSS-классов.
3. Визуальную проверку нужно было делать по реальным экранам обеих тем и ширин, а не только по исходным компонентам.

### Предложения по развитию

1. Держать одну тёплую нейтральную основу, один выразительный брендовый акцент и контрастные семантические статусы; не красить каждый блок отдельным цветом.
2. Сравнивать иерархию, плотность, сетку, состояния и типографику с Linear, Vercel и Stripe, но не копировать их бренд/контент.
3. Скриншоты хранить раздельно: реальный экран BeautyFlow, официальный референс и side-by-side-пара.
4. Для motion использовать GSAP только в оправданной сцене/scroll-переходе, Motion — для React-переходов и появления контента; уважать reduced motion и не анимировать каждое действие CRM.
5. Если центр уведомлений ещё не подключён к API, сообщать это честно и вести к реальным разделам, не придумывая события.

## Что уже сделано в этой ветке

- Создана тёплая система светлой/тёмной тем с глубоким сливовым акцентом, более читаемыми контролами и общими стилями поверхностей.
- Переработаны Landing, Auth-оболочка, общий sidebar/topbar, KPI-карточки и уведомления.
- Устранено глобальное перекрашивание ссылок при hover; Playwright подтвердил белый текст CTA на тёмно-сливовом фоне.
- Исправлены семантические фоны ячеек календаря для рабочих, нерабочих и заблокированных интервалов в обеих темах.
- Добавлены Motion и GSAP; лендинг загружается отдельным чанком, CRM не должна загружать scroll-анимации лендинга вместе с первой страницей приложения.
- Кнопка уведомлений открывает аккуратное пустое состояние со ссылками на реальные записи/оплаты.
- Исправлен demo URL в README.
- Созданы снимки `docs/screenshots/redesign/before/`, `after/`, официальных референсов `references/` и пары `comparisons/`.
- На ширине 390 px Playwright обнаружил переполнение входа/регистрации на 26 px и наложение футера на длинную форму регистрации. Исправлены минимальный размер grid-колонки и поток футера; повторный прогон подтвердил ширину 390 px без горизонтального переполнения на всех 7 публичных маршрутах в светлой и тёмной темах.
- В мобильной регистрации футер теперь следует после формы, поля не перекрываются. Снимки мобильных публичных маршрутов добавлены в side-by-side индекс; для входа/регистрации используется отдельный снимок Linear Login на мобильном.

## Ограничения, подтверждённые во время проверки

- Локальный Google OAuth config отвечает `enabled:false, clientId:null`. Пользовательский flow использует существующий API-контракт, но реальную авторизацию нельзя завершить без настроенных OAuth credentials; backend и контракты не менялись.
- Email-OTP вход был успешно пройден на демо-аккаунте. Повторные Playwright логины затем упёрлись в локальный cooldown/лимит; поэтому после исчерпания лимита CRM mobile снимки не перезапускались. Desktop CRM и модальные окна уже сняты, мобильные публичные страницы проверены на обеих темах.
- Production build проходит; остаётся предупреждение Vite о существующем основном чанке приложения (~1.31 MB до gzip) и обычные предупреждения bundler по `use client` из зависимостей.
- `npm run check:contrast` проходит пары токенов. Root typecheck раньше остановился на существующей несвязанной типизации `tests/api/login-verification.test.ts:93`; не исправляй это изменением backend/API/тестов.
