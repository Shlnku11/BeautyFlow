# PRODUCT_SPEC.md — Продуктовая спецификация

Продукт: **SaaS CRM для салонов красоты** (онлайн-запись, клиентская база, календарь мастеров, оплаты, напоминания, аналитика владельца). Основа — NextAppointments (Next.js/React/TypeScript). Reference-проект (Easy!Appointments, PHP) — только источник идей.

## 1. Роли пользователей

| Роль | Кто | Главная задача |
|---|---|---|
| **owner** | Владелец салона (один на бизнес) | Управлять бизнесом целиком: деньги, команда, настройки, аналитика |
| **admin** | Администратор/менеджер | Ежедневная работа: записи, клиенты, оплаты, расписания, услуги |
| **master** | Мастер | Видеть свой день, менять статусы своих записей, писать заметки после визита |
| **customer** (без аккаунта) | Клиент салона | Записаться онлайн, отменить/перенести по ссылке |

Матрица прав — PERMISSIONS_MATRIX.md.

## 2. Пользовательские сценарии (ключевые)

1. **Владелец регистрируется:** создаёт бизнес и владельца → добавляет мастеров и услуги → задаёт расписания → получает публичную ссылку `/b/<slug>`.
2. **Клиент записывается онлайн:** услуга → мастер/«любой» → дата → время → контакты → подтверждение + письмо; позже отменяет/переносит по ссылке.
3. **Администратор ведёт день:** видит календарь, создаёт запись по телефону, переносит, отмечает приход/неявку, принимает оплату.
4. **Мастер:** открывает «Мой день», завершает визит, оставляет заметку.
5. **Владелец анализирует:** dashboard (выручка, загрузка, популярные услуги, отмены, новые клиенты).
6. **Напоминания:** клиент получает письмо за 24 ч и за 1 ч; после визита — сообщение.
7. **Команда:** владелец/админ создаёт мастера (с email) — тот получает приглашение и входит; при увольнении доступ отключается. <!-- CHANGED: A2b --> *(MVP: создать admin и менять роли нельзя — post-MVP.)*
8. **Возврат денег:** администратор оформляет частичный/полный возврат; журнал сохраняет историю.

### 3a. Сокращения MVP относительно первого ТЗ <!-- CHANGED: A2b -->

Согласованы владельцем; подробности — MVP_SCOPE.md, риск №16 в MASTER_ARCHITECTURE §23:
1. **R3:** admin не создаётся, роли не меняются.
2. **R10:** нет отдельного журнала транзакций и карточки платежа (история = список оплат); возврат (`PAY-06`) **в MVP**.
3. **R11:** журнал отправок без UI, без повтора вручную, настройки видов по умолчанию.
4. **R12:** 4 KPI + ближайшие записи; без графика, загрузки мастеров, топа услуг.
5. Нет удаления клиентов, услуг, сотрудников (деактивация вместо удаления), нет смены имени профиля и переключения бизнесов.

## 4. Дополнительные функции (в MVP, но не из основного списка)

- Приглашение мастера по email — вместе с созданием сотрудника (`STF-02`), повторное приглашение и отключение (`MEM-04`, `MEM-03`); отдельное приглашение `MEM-02` и передача владения `MEM-05` — post-MVP. <!-- CHANGED: A2b -->
- Журнал аудита: **запись** чувствительных действий в `auditLogs` ведётся; просмотр владельцем (`AUD-01`) — post-MVP. <!-- CHANGED: A2b -->
- ~~Переключение между несколькими бизнесами одного пользователя~~ — **post-MVP** (`AUTH-05`); в MVP один пользователь — один бизнес. <!-- CHANGED: A2b -->
- Идемпотентность создания записей и оплат.

## 5. Ограничения MVP

- Один часовой пояс и одна валюта на бизнес; валюты — `RUB, KZT, KGS, USD, EUR`.
- Только русский интерфейс и письма (архитектура готова к `en`).
- Только email реально отправляется; SMS/push — интерфейсы без провайдеров.
- Оплаты — ручной учёт; без онлайн-эквайринга, фискализации, налогов.
- Один салон = один «бизнес» (филиалов/локаций нет).
- Запись — на одну услугу и одного мастера; комбо-услуги/цепочки — нет.
- Перенос записи — через диалог выбора слота (без drag-and-drop).
- Тёмной темы нет.
- Slug бизнеса неизменяем.
- Блокировка времени «на весь бизнес» — веер по текущим активным сотрудникам.
- Клиент записывается без аккаунта; личного кабинета клиента нет.

## 6. Явно вне объёма (out of scope)

Онлайн-платежи (Stripe/PayPal), абонементы/сертификаты/лояльность, склад и расходные материалы, расчёт зарплат/комиссий мастеров, филиалы и сети, групповые занятия/мероприятия (`attendants_number` reference), отзывы и рейтинги, маркетинговые рассылки, интеграции с Google/Apple/Outlook Calendar (кроме ссылок «добавить в календарь»), мобильные нативные приложения, импорт/экспорт CSV, слияние дубликатов клиентов, двухфакторная аутентификация, SSO, публичный API/webhooks, мультиязычность (кроме готовности архитектуры), биллинг самой SaaS-подписки, white-label/кастомные домены, drag-and-drop календаря, SMS/push-провайдеры.

## 7. Definition of Done

**Функция считается завершённой, только если выполнены все пункты:**
1. Реализованы модель (Mongoose + индексы через миграцию), сервис, Route Handler, UI-экран **без mock-данных**.
2. Контракт совпадает с API_CONTRACTS.md (поля, коды, права).
3. Права проверены тестами для всех трёх ролей; тест изоляции A vs B (404) пройден.
4. Unit + integration + API-тесты функции написаны и зелёные; для критичных потоков — E2E.
5. `lint`, `typecheck`, `build`, миграции проходят без предупреждений уровня error.
6. UI: состояния loading/empty/error/success, клавиатурная навигация, мобильная раскладка проверены; axe без серьёзных нарушений.
7. Нет секретов в коде/архиве; новые env-переменные описаны в `.env.example` и MASTER_ARCHITECTURE §15.
8. PROGRESS.md обновлён; изменения документов, если контракт менялся (с разрешения).
9. Код проверен Claude по чек-листу DEEPSEEK_HANDOFF_RULES §8 (для кода из внешних чатов).

**Продукт (MVP) готов, когда:** все R1–R14 покрыты по таблице MASTER_ARCHITECTURE §Covered requirements; сквозной сценарий (регистрация → настройка → публичная запись → email → календарь → оплата → dashboard) проходит E2E; пройдены тесты безопасности (TESTING_STRATEGY §10); выполнен деплой по инструкции.
