## ADR-001. MongoDB + Mongoose вместо PostgreSQL
**Статус:** Принято владельцем.
**Контекст:** ранее планировался PostgreSQL (RLS, композитные FK, exclusion constraint). Владелец выбрал MongoDB.
**Причины выбора MongoDB (учтены):** документная модель хорошо ложится на расписание мастера (вложенные интервалы/перерывы — один документ) и снимки (`serviceSnapshot`); простое локальное развёртывание и доступные управляемые варианты; единый язык и структура данных с JS/TS-стеком (Mongoose-схемы + Zod); меньше «ORM-магии».
**Что отвергнуто и почему:** PostgreSQL остаётся технически более строгим вариантом для финансовых и конкурентных данных; от него отказались **по решению владельца**, а не потому, что он не подходит. Мы не заявляем, что MongoDB «лучше», и фиксируем цену:
**Последствия/компромиссы:**
- Нет FK, RLS и exclusion constraint → замена: репозитории с `ctx`, tenant-plugin, проверка ссылок в сервисах, уникальный multikey-индекс `occupiedKeys` (ADR-004, 005), тесты A/B.
- Транзакции требуют replica set → Docker Compose поднимает одиночный replica set; тесты — `MongoMemoryReplSet`; production — Atlas или собственный replica set.
- Агрегации (дашборд) — через aggregation pipeline; сложные отчёты проще в SQL (пересмотр при росте).
- Индексы и «схема» управляются миграциями (ADR-015), а не автоматически.
- Деньги — целые minor units (нет Decimal-проблем).

## ADR-002. Next.js Route Handlers как backend
**Статус:** Принято владельцем.
**Решение:** backend — Route Handlers (`src/app/api/**/route.ts`) на Node.js runtime; тонкие обработчики → сервисы → репозитории. Отдельный Express-сервис не создаётся. Фоновые задачи — отдельный Node-процесс `scripts/worker.ts` (+ HTTP-эндпоинт для внешнего cron).
**Последствия:** один репозиторий и деплой; статический экспорт (`next export`, `output: 'export'`) **несовместим** — из текущего `build`-скрипта удаляется. Edge runtime не используется (Mongoose). Middleware — только UX-редирект, не механизм безопасности (известны обходы middleware в старых версиях Next; ADR-016).

## ADR-003. Аутентификация и сессии
**Статус:** Принято.
**Решение:** собственные cookie-сессии: случайный токен 32 байта, в cookie; в БД — `HMAC-SHA256(token, TOKEN_PEPPER)` (`sessions.tokenHash`); `HttpOnly`, `Secure` (prod), `SameSite=Lax`; скользящий срок 14 дней + абсолютный 90; TTL-индекс чистит просроченные. Пароли — **argon2id** (`@node-rs/argon2`; запасной вариант `bcryptjs` cost ≥ 12, если нативная сборка недоступна). Роль определяется на каждый запрос по `businessMembers`. CSRF: `SameSite=Lax` + проверка `Origin` + обязательный JSON `Content-Type`.
**Отвергнуто:** JWT в cookie/localStorage (сложнее отзыв, смена роли и отключение пользователя должны действовать мгновенно); Auth.js (избыточен для email+пароль, хуже контроль над мультитенантным контекстом).
**Последствия:** обращение к БД на каждый запрос (приемлемо, индекс по `tokenHash`); отзыв сессий тривиален; нужны rate limiting и сброс пароля (в MVP).

## ADR-004. Изоляция тенантов
**Статус:** Принято.
**Решение:** `businessId` берётся только из сессии (или slug/токена в публичных маршрутах). Четыре слоя: (1) `TenantContext` — обязательный первый аргумент репозиториев; (2) `tenantPlugin` Mongoose бросает ошибку при запросе без `businessId`; (3) сервис проверяет все ссылки в том же бизнесе; (4) тесты A/B, включая автоматический обход реестра маршрутов. Чужой объект → `404`.
**Последствия:** изоляция держится на дисциплине кода и тестах, а не на БД (в отличие от RLS). Риск «забыли фильтр» снижен guard-плагином и мутант-тестом (TESTING_STRATEGY §4). Опционально позже: отдельная БД на бизнес для крупных клиентов (не в MVP).

## ADR-005. Защита от двойной записи
**Статус:** Принято.
**Решение:** уникальный partial multikey-индекс по `appointments.occupiedKeys` (ключи 5-минутных ячеек занятого диапазона) + Mongo-транзакция с `$inc staff.bookingVersion` для согласованности с расписанием/блокировками + предварительная проверка движком. Подробно — DATA_MODEL §17, BOOKING_ENGINE_SPEC §7–8.
**Отвергнуто:** «проверить, затем вставить» (гонка); коллекция блокировок/lock-документы (лишняя сущность и очистка); глобальный лок на бизнес (лишняя конкуренция).
**Последствия:** все времена кратны 5 минутам; массив ключей до ~170 элементов на запись; перенос — единичный `updateOne`; инвариант проверяется race-тестами, включая негативный (без индекса тест падает).

## ADR-006. Часовые пояса
**Статус:** Принято.
**Решение:** UTC в хранилище; локальные правила (расписание, «сегодня», границы периодов) — в IANA-поясе бизнеса через luxon; длительности — абсолютные минуты; неоднозначное локальное время — первое вхождение, несуществующее — слот пропускается (BOOKING_ENGINE_SPEC §10). Публичный UI показывает время бизнеса с подписью зоны.
**Последствия:** клиент в другом поясе видит время салона (ожидаемо для офлайн-услуг); смена пояса бизнеса блокируется при будущих записях.

## ADR-007. Дизайн
**Статус:** Принято владельцем (стиль) / Принято (детали).
**Решение:** purple soft glassmorphism в умеренной дозе: стекло — sidebar, topbar, KPI-карточки, hero/вход, backdrop модалок; данные (таблицы, календарь, формы, модалки, графики) — на плотных поверхностях. Контраст проверен расчётом (DESIGN_SYSTEM). Тёмной темы в MVP нет. Токены — CSS-переменные, Tailwind ссылается на них.
**Последствия:** `backdrop-filter` стоит производительности → лимит стеклянных элементов, fallback и поддержка `prefers-reduced-transparency`.

## ADR-008. Платежи
**Статус:** Принято владельцем.
**Решение:** ручной учёт; `online` — только пометка метода; журнал `transactions` append-only, деньги движутся только через него; отчётность — из транзакций; частичный возврат без отдельного статуса. Stripe/PayPal добавляются позже как провайдер, создающий те же `payments/transactions`.
**Последствия:** нет сверки с банком/эквайрингом; ошибки исправляются возвратом и новым платежом (аудит сохраняется).

## ADR-009. Блокировка «на весь бизнес» = веер блоков по сотрудникам
**Статус:** Принято (компромисс).
**Контекст:** общий блок без `staffId` требует отдельной сериализации с записями.
**Решение:** `blockedPeriods.staffId` обязателен; блок для всех создаёт по документу на активного сотрудника с общим `groupId`; сериализация — тем же `staff.bookingVersion`.
**Последствия:** сотрудники, добавленные позже, не покрыты (UI предупреждает); удаление группы — `?group=true`.

## ADR-010. Очередь уведомлений и воркер
**Статус:** Принято.
**Решение:** коллекция `notifications` как очередь; claim через атомарный `findOneAndUpdate` с арендой (`lockedUntil`); дедупликация уникальным `dedupeKey`; повторы с backoff; два способа запуска (процесс-воркер или HTTP-эндпоинт за `CRON_SECRET`). Единственное исключение из tenant-guard — глобальный claim воркера; дальше работа идёт в контексте `notification.businessId`.
**Отвергнуто:** отдельный брокер (Redis/BullMQ) — лишняя инфраструктура для MVP; интерфейс провайдеров/очереди допускает замену.
**Последствия:** задержка отправки до интервала опроса (30 с); необходимо следить за воркером (алерты, NOTIFICATIONS_SPEC §7).

## ADR-011. Права master на блокировки и расписание
**Статус:** Принято (может быть смягчено).
**Решение:** master не создаёт блокировки времени и не меняет расписание — это делают owner/admin; master видит своё расписание и записи.
**Последствия:** меньше риск конфликтов и злоупотреблений; ценой удобства. Расширение (например, «master блокирует своё время») — отдельное решение и новый ключ права.

## ADR-012. Лицензирование и перенос идей из reference
**Статус:** Принято.
**Контекст:** Easy!Appointments распространяется по **GPL-3.0**; построчный перевод PHP в TS — производное произведение. В главном проекте нет файла `LICENSE`, хотя README называет проект открытым — лицензия исходника не определена.
**Решение:** reference используется как источник **идей**; поведение описано в этих документах своими словами и реализуется по ним. Разработчики (включая внешние чаты) не получают PHP-код и не переносят его; специфические фрагменты (SQL, тексты, структуры) не копируются. В репозиторий добавляется `NOTICE` с указанием обоих проектов и их лицензий. Лицензия самого продукта выбирается владельцем (**Decisions needed**).
**Последствия:** остаточный риск — подобие структур из-за общей предметной области; он снижается самостоятельным проектированием (другая модель данных, БД, язык). Это не юридическая консультация; перед коммерческим запуском — консультация юриста.

## ADR-013. Языки и локализация
**Статус:** Принято владельцем (русский основной) / Принято (механика).
**Решение:** все строки — в типизированном словаре `ru.ts` через `t()`; сервер возвращает **коды** ошибок, UI переводит; шаблоны писем ключуются по `locale`; даты/деньги — `Intl`. Библиотека (`next-intl` и др.) в MVP не подключается; добавление `en` = второй словарь + выбор локали.
**Последствия:** хардкод русского в компонентах запрещён (проверяется); полная многоязычность (маршрутизация по локали) потребует отдельного решения.

## ADR-014. Доступ UI к данным
**Статус:** Принято.
**Решение:** UI (включая Server Components) работает только через API (`api-client` + TanStack Query); прямой доступ к БД из UI запрещён.
**Последствия:** единый путь = единые проверки прав и изоляции, контракты тестируются так же, как используются UI; цена — меньше выгоды от RSC-стриминга на экранах с данными.

## ADR-015. Миграции для MongoDB
**Статус:** Принято.
**Решение:** собственный лёгкий раннер `migrations/NNN_name.ts` + коллекция `schemaMigrations` (id, checksum); миграции создают индексы и преобразуют данные; применённые миграции неизменяемы; `autoIndex: false`. Альтернатива (`migrate-mongo`) — допустима при согласовании.
**Последствия:** индексы не появляются «сами» — тестовое окружение применяет те же миграции.

## ADR-016. Версия Next.js и безопасность
**Статус:** Открыто (исполняется на Этапе 1).
**Контекст:** в проекте Next.js 14.1.0; известны уязвимости в этой ветке, включая обход проверок в middleware. Мы не полагаемся на middleware для безопасности (ADR-002), но обновление всё равно необходимо.
**Решение:** на Этапе 1 обновить Next.js до актуальной поддерживаемой версии (после проверки текущих релизов и совместимости с React/ESLint/Tailwind), не меняя архитектуру App Router.

## ADR-017. Версии платформы: Node.js 24 LTS и MongoDB 8.0
**Статус:** Принято владельцем. <!-- CHANGED: A2a -->
**Контекст:** в первоначальном ТЗ были указаны Node.js 20 LTS и MongoDB 6.0. Проверка по состоянию на 03.10.2026 (поиск по публичным календарям поддержки): Node.js 20 вышел из поддержки **30.04.2026**; Node.js 22 поддерживается до апреля 2027, Node.js 24 — до апреля 2028; MongoDB 6.0 вышла из поддержки **31.07.2025** (поддерживаемые линии включают 7.0 — до 31.08.2027, и более новые). Продукт с персональными данными клиентов не должен стартовать на версиях без патчей безопасности.
**Решение:** Node.js **24 LTS** (`.nvmrc` = `24`, `engines.node` = `>=24`, базовый образ Docker — Node 24, non-root) и MongoDB **8.0** (образ `mongo:8.0`, replica set `rs0`; в production — Atlas или собственный replica set той же линии). Next.js — актуальная поддерживаемая версия, **совместимая с Node 24**, выбирается и фиксируется в `package.json` на этапе 1 (ADR-016).
**Последствия и проверки:**
- Совместимость выбранных версий драйвера/Mongoose с MongoDB 8.0 (транзакции, multikey/partial-индексы, `$dateTrunc`) проверяется в **спайке этапа 0**; при несовместимости — правка версий, не архитектуры.
- Тестовая среда (`mongodb-memory-server`) должна запускать бинарь MongoDB 8.0 (при первом запуске требуется сеть либо предзагруженный бинарь/кэш в CI); без этого integration-тесты запускаются на `mongo:8.0` из Docker (`TEST_MONGODB_URI`).
- Даты окончания поддержки меняются: версии платформы пересматриваются при планировании post-MVP и не реже раза в год; точные даты 8.0/24 сверять по официальным источникам (nodejs.org, mongodb.com/legal/support-policy) перед релизом.
- Используемые возможности MongoDB (транзакции, `$dateTrunc`, partial-индексы) существуют и в 7.0 — откат на 7.0 возможен без изменения дизайна, если 8.0 окажется проблемной.

## Сводка важных компромиссов
1. MongoDB вместо PostgreSQL: изоляция и анти-двойная запись держатся на индексах, плагине и тестах, а не на RLS/exclusion.
2. Собственные сессии вместо готовой библиотеки: больше кода безопасности, зато полный контроль и мгновенный отзыв.
3. Сетка 5 минут: простота и жёсткая гарантия на уровне БД, но нельзя записывать на произвольные минуты.
4. Блок «на весь бизнес» как веер: простота ценой неполного покрытия будущих сотрудников.
5. Собственная очередь вместо брокера: меньше инфраструктуры, ограниченная пропускная способность (достаточно для MVP).
6. UI только через API: единообразие и тестируемость против части возможностей RSC.
7. Ручной учёт оплат: быстрый старт без эквайринга, без автоматической сверки.
8. Только email реально работает; SMS/push — интерфейсы.
9. Стеклянный стиль ограничен whitelist ради читаемости CRM.
10. Лицензионный риск снижается подходом «идеи, а не код», но не устраняется полностью.
