# PAYMENTS_SPEC.md — Оплаты, возвраты, журнал транзакций

Область MVP: **ручной учёт оплат** (администратор фиксирует, что клиент заплатил). Без Stripe/PayPal и без обработки карт. Метод `online` в MVP — лишь пометка способа («оплачено онлайн вне системы»); реальная интеграция добавляется отдельным провайдером позже (ADR-008). Данные модели — DATA_MODEL_MONGODB §14–15, эндпоинты — API_CONTRACTS §12.

## 1. Сущности и термины

| Термин | Смысл |
|---|---|
| **payment** | Платёж по записи: «клиент обязан/внёс сумму X способом M». Изменяемое состояние (статус, `refundedMinor`) |
| **transaction** | Неизменяемая строка журнала движения денег: `charge` (приход) или `refund` (возврат) |
| **balance** | Остаток по записи: `serviceSnapshot.priceMinor − (Σ paid − Σ refunded)` |

Правило: **деньги двигаются только через `transactions`**. Любая отчётность (дашборд, выручка клиента, итоги платежей) считается из `transactions`, а не из полей `payments`.

## 2. Методы и статусы

Методы: `cash`, `card`, `transfer`, `online`.

Статусы платежа и переходы:

| Из \ В | pending | paid | refunded | cancelled |
|---|---|---|---|---|
| (создание) | ✔ | ✔ | — | — |
| pending | — | ✔ `mark-paid` | — | ✔ `cancel` |
| paid | — | — | ✔ полный возврат | — |
| refunded | — | — | — | — |
| cancelled | — | — | — | — |

- Частичный возврат: статус остаётся `paid`, растёт `refundedMinor`. «Частично возвращён» — **производное** состояние (`paid ∧ 0 < refundedMinor < amountMinor`), отдельного статуса нет.
- `refunded` — только когда `refundedMinor = amountMinor`.
- `cancelled` возможен только из `pending`; оплаченный платёж не отменяется, а возвращается.
- Любой другой переход → `409 INVALID_PAYMENT_TRANSITION`.

## 3. Правила

1. Оплата привязана к **записи** (`appointmentId` обязателен); `customerId` и `staffId` копируются с записи при создании и не меняются. Оплату по `cancelled` записи принять нельзя (`409 APPOINTMENT_CANCELLED`); по `no_show` — можно (например, штраф).
2. Несколько платежей на одну запись разрешены (предоплата + доплата).
3. Переплата не блокируется (чаевые, ошибка ввода), но UI показывает отрицательный баланс предупреждением.
4. Валюта платежа = валюте бизнеса. Смена валюты бизнеса запрещена при наличии записей/платежей будущего (SET-02) и вообще не меняет прошлые платежи.
5. `amountMinor` — целое > 0. После `paid` сумма и метод **неизменяемы**; ошибки исправляются возвратом и новым платежом.
6. `paidAt` по умолчанию = сейчас; админ может указать прошлую дату (не в будущем, не раньше создания записи −365 дней).
7. Каждая операция с деньгами выполняется в **Mongo-транзакции**: изменение `payments` + вставка `transactions` атомарны.
8. Идемпотентность: заголовок `Idempotency-Key` на `POST /api/payments` → повтор возвращает существующий платёж, вторую `charge` не создаёт.
9. Возврат: `amountMinor ≤ amountMinor(платежа) − refundedMinor`; обязательная `note`; гонка двух возвратов исключается условным обновлением `updateOne({_id, refundedMinor: прежнее, status:'paid'}, {$inc…})` — при несовпадении `409`.
10. Все эндпоинты оплат доступны только owner/admin (PERMISSIONS_MATRIX: `payments:*`, `transactions:read`). master деньги не видит.

## 4. Журнал транзакций (append-only)

- Типы: `charge` (direction `in`), `refund` (direction `out`).
- Создаются: при создании платежа со статусом `paid` (`charge`), при `mark-paid` (`charge`), при возврате (`refund`). Отмена `pending` не создаёт транзакций (в журнал попадает только движение денег; факт отмены — в `auditLogs: payment.cancelled`).
- Неизменяемость: нет эндпоинтов update/delete; Mongoose-хуки запрещают изменение/удаление (`ImmutableDocumentError`); в production — отдельный пользователь БД без прав `update`/`remove` на `transactions`.
- Исправление ошибки: компенсирующая запись (`refund`) + новый платёж; прежние строки остаются.

## 5. Фильтры и поиск (`PAY-01`; журнал `TRX-01` — post-MVP) <!-- CHANGED: A2b -->

**MVP:** «история транзакций» — это список оплат `PAY-01`. Итоги `PAY-01 meta.totals` считаются **по платежам выборки** (платежи, оплаченные в выбранный период по `paidAt`): `paidMinor` = Σ`amountMinor` платежей со статусами `paid`/`refunded`, `refundedMinor` = Σ`refundedMinor` тех же платежей. Это **не равно** выручке дашборда (`DSH-01`, по движению денег `transactions.occurredAt`), если возврат оформлен в другом периоде, чем оплата; различие намеренное и описано в DASHBOARD_SPEC §7 (кейс 9). Отдельный журнал движений `TRX-01/02` (с итогами in/out/net по `occurredAt`) — post-MVP.

Период (в поясе бизнеса, границы `[from 00:00, to+1д 00:00)`), метод, статус/тип, мастер, клиент (`customerId`), поиск `q` по имени/телефону клиента (сначала префиксный поиск клиентов через `searchTokens`, затем фильтр по их id — максимум 200 id, иначе просьба уточнить запрос), просмотр записи и пользователя, принявшего оплату (`createdBy`).

## 6. Отчёты (в MVP)

| Отчёт | Формула | Где |
|---|---|---|
| Выручка (нетто) за период | Σ `charge` − Σ `refund` по `occurredAt` | MVP: `DSH-01`; post-MVP: `TRX-01 meta.totals` |
| Выручка по методам | группировка по `method` | MVP: фильтр `method` в `PAY-01`; post-MVP: `TRX-01`; экспорт вне MVP |
| Выручка клиента | Σ `charge` − Σ `refund` по `customerId` | CUS-03 `summary.totalPaidMinor` |
| Выручка по услугам | через `appointments.serviceId` ($lookup по `appointmentId`) | post-MVP (`DSH-04`) |
| Должники/баланс записи | `serviceSnapshot.priceMinor − net` | MVP: поле `payment.balanceMinor` в `APT-03`/`CAL-01`; отдельный `PAY-07` — post-MVP |

Экспорт CSV, закрытие смены, налоги, фискализация — **вне MVP**.

## 7. Права и аудит

owner/admin: создание, mark-paid, отмена pending, возврат, просмотр. Аудит: `payment.created`, `payment.cancelled`, `payment.refunded` (метаданные: `paymentId`, сумма, метод; без персональных данных клиента).

## 8. Тесты (минимум)

Unit: переходы статусов (все недопустимые пары); расчёт баланса; расчёт нетто; частичный/полный возврат; границы сумм.
Integration (replica set): (1) `paid` создаёт ровно одну `charge`; (2) `mark-paid` дважды → одна `charge`; (3) идемпотентный повтор; (4) две параллельные частичные возврата на сумму > платежа → один успешен/сумма не превышена; (5) сбой между апдейтом платежа и вставкой транзакции откатывает оба (симуляция ошибки); (6) попытка update/delete `transactions` через модель → ошибка; (7) оплата по чужой записи (бизнес B) → 404; (8) `customerId/staffId` берутся с записи, не из тела; (9) master → 403 на все `PAY-*`; (10) выручка в дашборде `DSH-01` = Σ`charge` − Σ`refund` по `transactions.occurredAt` периода (**прямой запрос к БД**; `TRX-01` — post-MVP), `PAY-01 meta.totals` проверяется отдельно по своему определению (§5), в т.ч. случай возврата в следующем периоде; (11) границы периода в нестандартном часовом поясе (+DST); (12) `PAY-04`: `pending → paid` создаёт `charge`, повтор — одну; `PAY-05`: отмена `pending` не создаёт транзакций, отмена `paid` → 409; (13) `PAY-02` по записи `cancelled` → 409 `APPOINTMENT_CANCELLED`. <!-- CHANGED: A2b -->
E2E: «принять оплату → видна в списке оплат (истории) → вернуть часть → баланс обновился»; «создать платёж «Ожидает оплаты» → отметить оплаченным».
